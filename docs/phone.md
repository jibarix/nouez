# Working from your phone

Part of [nouez's documentation](../README.md#documentation).

The [README](../README.md#from-your-phone) shows what to ask the dispatcher; this page has the detail.

## A new Claude Code session from your phone

From the Claude app, ask the dispatcher, or any session with nouez, for another one: *"open a new Claude session for C:/Users/me/Projects/other"*. Claude calls `OpenClaudeSession`, which opens a new terminal window on the computer and starts `claude --remote-control <name>` in that folder. The new session shows up in the app's session list a few seconds later. It is an ordinary session that saves its transcript and can be resumed. A `claude` you start from Claude Code's own shell doesn't save its transcript, because it inherits `CLAUDE_CODE_CHILD_SESSION` and the other variables that mark it as a child session. `OpenClaudeSession` starts it without them, keeping any variable you set yourself in your environment. On Linux it needs a graphical desktop (an X or Wayland display): over SSH, or in tmux without one, no window can open. The folder can be a new one: *"open a new Claude session in a new folder C:/Users/me/Projects/economic-recession"* makes Claude pass `create: true`, and nouez creates it (its parent must exist). To pick up an earlier conversation, ask *"resume my hours-tracker session"*: Claude shows you that folder's conversations from `ListClaudeSessions`, newest first and each marked open or not, and passes the id of the one you pick as `resume`. The window runs `claude --resume <id>` with Remote Control, so the conversation carries on where it stopped. A conversation already open in a running session is never opened twice. Claude Code's experimental Code Mode doesn't run with Remote Control, and a conversation held in Code Mode resumes only in a terminal with Code Mode on, so `resume` can't bring one back as a remote session.

To choose a conversation, ask *"show my earlier hours-tracker conversations"* The dispatcher lists the ten most recent in that folder with their last activity, id, whether each is open, and any custom title and git branch. Ask for up to 50, then tell it which one to resume.

Claude Code asks whether you trust a folder the first time it runs there, and a session waiting at that question can't connect to the app. So before opening a window, nouez checks Claude Code's settings (`~/.claude.json`). If the folder isn't trusted, nothing opens: the result gives a report of what the folder's project settings would make Claude Code run or allow, and Claude shows it to you and asks whether you trust the folder. The report covers `.claude/settings.json`, `.claude/settings.local.json` and `.mcp.json` in the folder trust would be recorded for, the checkout the session opens in (they differ for a worktree) and the folder itself: hooks with their events, matchers and commands, the status line and helper commands, the names of variables set in `env` (not their values), permission rules and mode, extra folders, MCP servers with their commands or URLs (the names of their variables and headers, not the values), plugins marked on or off, marketplaces with their sources, and the name of any setting it doesn't know. Values that look like passwords or keys (in a URL, or after a flag such as `--token`) show as `***`, characters that don't print are spelled out, and a report that had to shorten an entry or a list says it is a summary. The report is read from files in the folder, so Claude is told to treat it as data. A file it can't read is reported as such, never as nothing, and then nouez won't record trust from the phone at all: you look at the file on the computer. If you say yes, Claude calls it again with `trust: true`, and nouez records your answer in `~/.claude.json` the way Claude Code's trust dialog does, then opens the window, so this works from your phone. nouez records trust only for a folder whose report the same nouez server has given earlier (Claude Code runs one per session, so in practice the same conversation), and only if not a byte of those files has changed since (it keeps a fingerprint of them, not the report's text); otherwise `trust: true` gets the report again and records nothing. A folder the same call creates, outside a git repository, has no settings, so it needs no report. Before each change nouez saves a dated copy of the file (the newest 20 are kept, in `%LOCALAPPDATA%\nouez\claude-json-backups`, or `$XDG_STATE_HOME/nouez/claude-json-backups` elsewhere, by default `~/.local/state/nouez/claude-json-backups`) and the result names it. Only that one setting changes. If you're at the computer, Claude can instead open the window untrusted (`open_untrusted: true`) so you answer Claude Code's own question there. nouez can prove Claude received the report, not that you read it. To approve each recording yourself, set `NOUEZ_ASK_TRUST=1`: nouez then asks in Claude Code's own prompt, naming the report's id, and records nothing unless you accept (a client that can't show the prompt is refused). If you'd rather nouez never record trust, set `NOUEZ_NO_TRUST_WRITE=1` in its environment, and `trust: true` is refused for a folder that isn't already trusted on its own, so you answer on the computer. Trust works like Claude Code's: outside a git repository, trusting a folder covers the folders inside it, but a git repository is trusted on its own (for a worktree, its main checkout), so trusting `C:/Users/me/Projects` doesn't cover a repository in it. Even in a trusted folder Claude Code can still ask on the computer: a project's own `.claude/settings.json` allow rules need that folder itself trusted, not just a folder above it, and a project's `.mcp.json` servers have their own approval. So a folder trusted only through one above it that has its own `.claude/settings.json` is treated like an untrusted one: nothing opens, and you get the report and the question. The result mentions `.mcp.json` servers when the file is there, and says when nouez can't tell whether a folder is trusted (Claude Code's settings can't be read, or the git layout is unusual).

To see what's running, ask any session *"which Claude sessions are open?"*. `ListClaudeSessions` lists the interactive Claude Code sessions registered in your Claude Code config folder, whoever started them, each with its name, folder, status and whether Remote Control is on. To close one, such as a stuck one, say which: *"close hours-tracker"*. `CloseClaudeSession` ends its `claude` process. On Windows, a session `OpenClaudeSession` opened also gets its window closed. Elsewhere nouez ends only the `claude` process: a window `OpenClaudeSession` opened then closes if the terminal closes when its command ends, as most Linux terminals do, and stays at a prompt otherwise (macOS Terminal). A session you started yourself leaves its terminal at the shell prompt. On macOS and Linux nouez first checks with `ps` that the process is still Claude Code, started no later than the session was registered, and isn't one nouez itself runs under; if it can't confirm that, it signals nothing and says why. The transcript stays, so `claude --resume` in that folder picks it up again. Claude shows you the list and closes only the sessions you pick, one call each, and never the one you're talking to. The list comes from `~/.claude/sessions`, which Claude Code keeps but doesn't document, so a future Claude Code version could change it.

To find a project, ask *"which projects do I have?"*. `ListProjects` lists the folders in the folder that holds the session's own (in the dispatcher, those in each of its projects folders), or in another folder you name: for each, whether it is a git repository, whether Claude Code is trusted there (itself, or through a folder above it), the Claude Code sessions running in it and which project settings files it has. Hidden folders (a name starting with a dot, or marked hidden on Windows) are left out. It reads the disk each time, so a folder you add shows up at once.

Claude Code's sign-in on the computer lasts a set time; using Claude Code doesn't extend it, and Claude Code says it ends on a day between two dates. A Remote Control session that outlives it disconnects until you sign in again, and signing in needs the computer. So nouez reads the line `claude auth status --text` prints about it (`Sign-in ends: between … and …`, with the exact end in parentheses; the earlier date is 3 days before it), keeps only that line, and from 7 calendar days before the earlier date adds a warning to the results of `OpenClaudeSession`, `ListClaudeSessions` and `ListProjects`, with how to renew (`claude auth login` in a terminal on the computer, or `/login` in a session there). `ConsultantBudget` always shows the line, and the status screen's top bar always shows the date to renew by and the days left, grey until the warning is on, then amber and red. It reads the line in the background when a server starts and then about once an hour (every 10 minutes in the last week), and again when Claude Code's credentials file changes (nouez looks only at the file's time, never inside it), so other tools don't wait for it; `ConsultantBudget` waits for a reading that is due, up to about 25 seconds. It saves the line in `nouez/claude-login.json` for every nouez server to share, with Claude Code's config folder and the names of any sign-in variables (such as `ANTHROPIC_API_KEY`, never their values), so a server signed in another way doesn't use it. It shows nothing when you sign in another way (an API key, say) or when your Claude Code doesn't print the line. Set `NOUEZ_NO_LOGIN_CHECK=1` to turn it off.

To see the [status screen](status-screen.md#usage-log-and-status-screen) on the computer, ask for it: `OpenStatusScreen` opens `server.py top` in a new terminal window there, with 1, 7 or 30 days of consultations or all of them, or switches the one already open to the page asked for, its usage or its consultations. It shows only on the computer; from the phone, ask for `ConsultantBudget` instead.

## The phone dispatcher

Remote Control on its own works like this. While `claude remote-control` runs in a folder on your computer and is connected, the Claude app offers the computer: tap new session, pick it, and the session runs there. That server starts every new session in its own folder (or, with `--spawn worktree`, in a new worktree of it); the app has no folder picker for it. Reaching a second project means starting another server in that project's folder, at the computer, and after a restart or a sign-out none is running until you start it again. (The Claude desktop app can offer several registered folders instead, while it is open.)

With nouez, one server, the dispatcher, reaches every project: a session in it opens a session in any folder with `OpenClaudeSession`, makes a folder for a new project, and records your trust answer, all from the phone. It records trust only for a folder inside one of its projects folders (by default the one that holds the dispatcher's; [Setup](setup.md#setup), step 3, names others with `--projects`, or none with `--no-projects`), spelled exactly as it is there (or on Windows, with no link on the way, as it is on disk), with no link below it, and for a git worktree only when its main checkout is in there too: the supervisor gives those folders to the dispatcher's nouez, which refuses any other, and refuses all when it wasn't given them (a dispatcher started by nouez 0.26.0 or older, until `dispatcher install`, with the `--folder` you installed it with, restarts it) or was set up with `--no-projects`. It never records trust in a projects folder that is a drive's root or is or holds your home folder, Claude Code's settings folder, nouez's cache or `~/.nouez`, also where a link takes them, or the temporary folder nouez's cache can fall back to, which `dispatcher setup` refuses. The one-time run in [Setup](setup.md#setup), step 3, is plain Claude Code without this limit, so stop it once the app lists the computer. [Setup](setup.md#setup), step 3, sets it up; this is how it runs.

**What runs.** At sign-in the system starts `server.py dispatcher run` (with `pythonw` on Windows, so no window shows). That supervisor runs `claude remote-control --name dispatcher --spawn same-dir` in the dispatcher folder, hidden, and keeps it running:

- It runs the `claude` on your `PATH`, or where Claude Code's installer puts it (`~/.local/bin`; on macOS also `/opt/homebrew/bin` and `/usr/local/bin`), since a program started at sign-in can have a shorter `PATH` than a terminal. On macOS the launch agent carries the `PATH` `install` ran with, and on Linux the supervisor started at sign-in puts that `PATH`, saved in `dispatcher-path`, ahead of the desktop's, so a `claude` from npm or nvm is found too. It clears the variables that would mark it as a child of another Claude Code session, as `OpenClaudeSession` does, and puts `claude`'s folder on the `PATH` it gets, so the sessions it opens find `claude` too.
- It reads what `claude` prints as it prints it, the status line it redraws in place included, to tell when it is connected (a status line such as `·✔︎· Connected · dispatcher`; `Connecting`, `Reconnecting`, `Disconnected` or `Not connected` there mean it isn't, and a line that only mentions the word changes nothing), and writes that output, without terminal codes and without the status line `claude` redraws every few seconds, to `dispatcher-claude.log` in nouez's cache folder; its own events go to `dispatcher.log`. Each log moves to `<name>.1` past 1 MB, replacing the one before; a log whose `<name>.1` isn't a plain file stops growing instead.
- When `claude` ends, it starts it again after 30 seconds, then twice as long each time up to 15 minutes, and after 30 seconds again once a run has lasted 10 minutes. A `claude` that hasn't connected within 5 minutes is ended and started again later: it is most likely waiting at a question no one can answer, so run the command in Setup step 3 in a terminal again and answer it (`dispatcher-claude.log` shows the question).
- Only one supervisor runs per user: a second one, started by hand or by a second sign-in, exits at once. When the supervisor stops, `claude` stops with it, with the conversations it started from the app: on Windows through job objects, one the supervisor is in, which ends what is left when the supervisor ends, killed included, and one per run that holds `claude` from its start; elsewhere by its process group, signalled until nothing in it runs, with `claude` collected only after that, so the group's id can't pass to another process meanwhile (the supervisor doesn't let `SIGCHLD` be ignored, and a `claude` something else collected anyway has its group left alone). Each run's processes are ended before the next starts, even when `claude` itself exited first. On Windows a supervisor that can't put itself in its job exits without starting `claude`. If the supervisor is killed on macOS or Linux rather than stopped, its `claude` can keep running; doctor then notes it as another Remote Control server. The windows nouez opens from the dispatcher (sessions and the status screen), its window arranger and the Codex daemon leave those jobs and keep running; started anywhere else, what nouez starts stays in its caller's job, apart from Antigravity's turns, which leave it as before.
- `install` and `uninstall` stop a running supervisor by leaving a request, `dispatcher.stop` in nouez's cache folder, which it looks for every second; they never end a process by its id. Only a plain file counts as that request: a folder or link of that name stops `install` and `uninstall` with a message, keeps a supervisor from starting `claude`, and shows as a problem in doctor and `status`.

**Is it there?** `server.py dispatcher status` says whether the supervisor runs, whether `claude` is connected or when it starts again, and shows the last lines of its log. `server.py doctor` checks the folder, its rules and trust, the sign-in start (there, turned off, or not nouez's) and the connection, and the status screen's top bar has a badge: green `● dispatcher` while connected, amber while it isn't, red when the supervisor ended without being asked to (it crashed, was killed, or couldn't check its sign-in start), and none once it was stopped, as `uninstall` does. `doctor` checks trust in the Claude Code profile the supervisor runs with.

**The folder's files.** `dispatcher setup` writes `CLAUDE.md` only when the folder has none, so edit it as you like; delete it and run `setup` again for nouez's current one. Ask “which reviews need me?” for a short list in the phone chat: one line per consultant with its project, state, age, kind and verdict, never the messages. First come finished turns whose reply Claude hasn't fetched (“done, no reply logged”, which a reply you only read on the status screen still shows), changes, no or incomplete verdicts from the last day, and turns running for ten minutes. The rules it adds to `.claude/settings.json` allow `mcp__consultants__OpenClaudeSession`, `ListClaudeSessions`, `ListProjects`, `CloseClaudeSession`, `ListConsultants`, `ConsultantBudget`, `OpenStatusScreen` and `ArrangeWindows`. `setup` only adds rules: those already in the file, and your user settings, still apply there. They name nouez's tools as `consultants`, the name Setup registers it under; `setup` says so if Claude Code doesn't run nouez by that name there. When an update adds a tool, the supervisor adds its rule before it next starts `claude` (after the computer restarts, or `dispatcher install` again), backing the file up first. It does that only while the file still has every rule an earlier nouez gave it, and once per rule, so a rule you take out stays out; otherwise run `setup` again. When a newer nouez is released, the dispatcher's tools say so in the phone chat, once per chat. (The supervisor marks the dispatcher's `claude` with `NOUEZ_DISPATCHER=1` for this; if you set `CLAUDE_CODE_MCP_ALLOWLIST_ENV=1`, Claude Code passes MCP servers only the variables it allows, so the mark doesn't arrive and the dispatcher's tools carry no notice.) Updating takes the computer: pull or download it there (see [nouez updates](setup.md#nouez-updates)), then run `dispatcher install` again, the way you first ran it, which starts the dispatcher again and ends the chats it has open. To use another folder or other projects folders, pass the same `--folder` and `--projects` (or `--no-projects`) to `setup` and `install`; `dispatcher status` and doctor show the projects folders the running dispatcher has.

**A sign-in start of your own.** If you set up a `claude remote-control` yourself before nouez had one, doctor notes it as another Remote Control server running, by its process id and `--name` only. The name is read from the process's own arguments, so a prompt that merely mentions `remote-control` is never taken for a server; on systems other than Windows, macOS and Linux, where only `ps`'s joined line is there, doctor gives the process id alone. Remove your own sign-in start (a Task Scheduler task, a launch agent, a systemd service), or the app lists the computer twice.

**Limits.** The computer must be on, awake and signed in: the dispatcher starts at your sign-in, not at boot, and a sleeping laptop is out of reach. A locked screen doesn't stop it, but reaching a locked computer from the phone hasn't been tested with nouez. Remote Control connects out to Anthropic; with Claude Code 2.1.330 the server listened on no port. Starting at sign-in was tested live on Windows; on macOS and Linux the launch agent and autostart entry are covered by tests only.

What we saw with Claude Code 2.1.330, in a conversation the server started from the app: `/exit` isn't available there ("isn't available in this environment"). Archiving the conversation in the app ended that conversation's process on the computer, while `claude remote-control` kept running (it showed "Ready" and 0 of 32 sessions), so the computer stayed in the app and a new conversation could start there. Sessions `OpenClaudeSession` opens run in their own terminal windows and weren't part of that test.

The dispatcher has no window on the computer. To follow its conversations there, open https://claude.ai/code in a browser signed in to the same account: it lists the Remote Control sessions as the phone app does.
