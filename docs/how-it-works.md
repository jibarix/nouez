# How it works

Part of [nouez's documentation](../README.md#documentation).

`codex app-server proxy` relays stdio to the daemon's control socket, which speaks JSON-RPC over WebSocket. The server does the WebSocket handshake and framing itself, opens one short-lived connection per tool call, and polls the turn until it finishes. Sessions the bridge starts are tagged with `threadSource: "nouez"`, so it can find them again after the daemon unloads them and so `StopConsultant` knows which ones it may archive.

For the Claude Code session tools, nouez doesn't talk to Claude Code at all. `OpenClaudeSession` opens a terminal window that runs `server.py claude`, which clears the variables Claude Code sets to tie its commands to its session and starts `claude --remote-control`. It runs the `claude` on your `PATH`, never one in the project folder. `ListClaudeSessions` reads the registry Claude Code keeps in `~/.claude/sessions`. On Windows it checks that each process is still the one that wrote its entry; elsewhere it lists those whose process exists, and `CloseClaudeSession` checks the program and start time before it signals one. `CloseClaudeSession` ends the chosen process. [docs/architecture.pdf](architecture.pdf) has the details.

## Files nouez keeps

Everything is on your computer, under your user account. The cache folder is `%LOCALAPPDATA%\nouez` on Windows and `$XDG_CACHE_HOME/nouez` or `~/.cache/nouez` elsewhere (a relative `XDG_CACHE_HOME` is ignored). On macOS and Linux nouez makes that folder readable by you only (0700). If it can't (the folder is another user's or a link), nouez uses `nouez-<uid>` in the temp folder instead, made private the same way, and says so. The dispatcher's files (`dispatcher.*` and `dispatcher-*` below) are the exception: they are always in `%LOCALAPPDATA%\nouez` as Windows itself reports it, or `~/.cache/nouez` in the home folder the system's user list names, whatever `LOCALAPPDATA`, `XDG_CACHE_HOME` or `HOME` say, so the supervisor started at sign-in and the commands you run from any shell use the same files. If that folder isn't a private folder of yours, the dispatcher commands stop with a message rather than use another.

| File | What | Kept |
|---|---|---|
| `usage-log.jsonl` | One line per consultation event: model, effort, kind, reason, the `base` of a branch review, tokens; never message text. Off with `NOUEZ_NO_USAGE_LOG=1`. `usage-log.jsonl.lock` is held while it is renamed. | Renamed with the date each month or past 20 MB; a renamed log deleted a year after it was last written, or sooner past 100 MB in all |
| `codex-locks/<thread id>.lock` | Empty; held while a server sends to or stops that Codex consultant, so a stop in one Claude Code session can't archive it as another starts a turn | Kept, since deleting one while another server opens it could let both hold it; each is empty |
| `agy/<id>/` | Each Antigravity consultant: its record (`consultant.json`: folder, name, model, standing instructions, agy conversation id), and each turn's message and output (`turns/`) | Turns deleted 90 days after you stop the consultant; its record stays until you delete it |
| `replies/reply-<turn id>.md` | The full text of a reply longer than 60,000 characters, or 20,000 when the waiter (`server.py wait`) prints it | 14 days |
| `patches/<sha256>.patch` | The diff saved for `revision: true`, named by the first 16 hex digits of its SHA-256. With `base` it includes committed changes since the merge base and any uncommitted changes. Even a clean tree can produce a patch containing deleted lines. For an Antigravity review, `attach_diff: true` sends the patch text to Google | 14 days |
| `claude-usage.json` | Claude Code's usage windows, written by `server.py statusline` | Replaced on each update |
| `usage-weeks.json` | The weekly token counts `server.py top` read from Claude Code's and Codex's own files, so later runs read only what was added | Replaced on each run of `top` |
| `claude-login.json` | The sign-in line from `claude auth status`, when it was read, the credentials file's time, Claude Code's config folder and the names of any sign-in variables set. Off with `NOUEZ_NO_LOGIN_CHECK=1`. | Replaced about hourly |
| `aa-models.json` | Model scores from Artificial Analysis, with a key set | Replaced about weekly |
| `latest-release.json` | The latest nouez release seen on GitHub | Replaced about daily |
| `pane-key` | The local key that made the token in each Codex pane nouez opened up to 0.22.0, so a server can find those panes and close them | Kept |
| `status-screen.lock`, `status-screen.json` | Held and written by the open status screen (its process id, an id of its own and the last request it applied), so `OpenStatusScreen` switches it rather than opening another; `status-open.lock` is held while one opens | The `.json` deleted when the screen closes |
| `status-command.json`, `status-command.lock` | The page and period `OpenStatusScreen` or a second `server.py top` last asked the open status screen for, addressed to that screen by its id and numbered after the one before it; the `.lock` is held while one is written, and while a screen opens or closes | Replaced on each request |
| `windows/s<session>/<pid>-<start>.json` | Windows only, one folder per Windows sign-in: each window nouez opened that is still open (its window handle, process, kind, place in the grid and box), and `screen.json`, the name of the screen the grid is on. `pass.lock` there is held while the windows are arranged. | Deleted when the window closes, or when a server starts and finds its process gone; `screen.json` when the last window closes |
| `arrange.json` | Whether nouez arranges its windows by itself (`ArrangeWindows` `auto`) | Kept |
| `dispatcher.lock`, `dispatcher.json` | Held by the running dispatcher supervisor, so only one runs; and what it is doing (its process id and `claude`'s, the folder, connected or not and since when, the next start) for `dispatcher status`, doctor and the status screen | Replaced as it changes |
| `dispatcher.log`, `dispatcher-claude.log` | The supervisor's events (starts, exits, connections), and what its `claude remote-control` printed, without terminal codes or the redrawn status line | Each moved to `<name>.1` past 1 MB, replacing the one before |
| `dispatcher-rules.json`, `dispatcher-rules.lock` | The allow rules for tools an update added that each dispatcher folder has had (granted by `setup` or the supervisor, or found there), so the supervisor adds each at most once; and held while one of them rewrites it | Kept |
| `dispatcher.stop`, `dispatcher-install.lock` | The request `install` and `uninstall` leave for the running supervisor to stop; and held while one of them changes the sign-in start, so two don't mix | The request deleted once the supervisor has stopped, or by the next supervisor that finds one left over |
| `dispatcher-autostart` | Linux only: where `dispatcher install` put the autostart entry, so `uninstall` and `status` find it whatever `XDG_CONFIG_HOME` says then | Deleted by `dispatcher uninstall` |
| `dispatcher-path` | Linux only: the absolute folders of the `PATH` `dispatcher install` ran with, `claude`'s folder first, which the supervisor started at sign-in puts ahead of the desktop's once it may start `claude` (an autostart entry can't carry a `PATH`). `install` stops if they don't fit on one line of 64 KB, or if `claude`'s folder has a `:` in its name; `status` and doctor say when the file isn't one `install` saved, and the desktop's `PATH` is used then | Replaced by each `install`; deleted by `dispatcher uninstall` |
| `dispatcher-task-<random>.xml` | Windows only: the scheduled task's definition while `dispatcher install` registers it, a new name each time | Deleted once registered |
| `claude-json-backups/` | Dated copies of `~/.claude.json` from before `OpenClaudeSession` recorded trust (`$XDG_STATE_HOME/nouez` or `~/.local/state/nouez` on macOS and Linux) | The newest 20 |

`dispatcher setup` also leaves files outside the cache folder: the dispatcher folder's `CLAUDE.md` and `.claude/settings.json`, and a dated copy of a `settings.json` it changed (`settings.json.nouez-<date>-<time>.bak`, beside it, kept until you delete it). `dispatcher install` adds the sign-in start: the Task Scheduler task `nouez dispatcher`, `~/Library/LaunchAgents/io.github.jibarix.nouez.dispatcher.plist` or `~/.config/autostart/nouez-dispatcher.desktop`; `dispatcher uninstall` removes it.

Old replies, diffs and renamed usage logs go when a server starts and when a new one is saved, old Antigravity turns when a server starts, and extra backups when a new one is saved. nouez trusts the cache folder itself, and below it writes, deletes and locks nothing through a link or a junction. `OpenClaudeSession` also passes a first prompt through a private temporary file (0600) that the new window deletes once read. Codex keeps its own sessions in `~/.codex`, Antigravity its conversations in its own folder, and Claude Code its transcripts in `~/.claude`; nouez doesn't move or copy them.

Over the network, nouez itself talks only to GitHub, for the latest release, and Artificial Analysis, only with a key set; neither gets anything from your projects or sessions. Everything else goes through the CLIs it runs: the local Codex daemon (which talks to OpenAI with your messages, as Codex always does); `agy`, which sends your messages to Google, and whose `/usage` call asks Google for your quota without a model turn; Claude Code, whose sessions run with Remote Control and whose `claude auth status` gives the sign-in line; and git, which runs your repository's clean filters while taking a diff. [SECURITY.md](../SECURITY.md) lists when each happens.
