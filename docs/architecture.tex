\begin{abstract}
\noindent nouez is an MCP server that lets Claude Code consult live Codex sessions, and open, list and
close Claude Code sessions on the same computer. This document
describes how the pieces fit together, with an example of every message nouez sends
or acts on at each boundary: the MCP traffic between Claude Code and nouez, the WebSocket
JSON-RPC traffic between nouez and the Codex app-server daemon, the commands nouez runs on
the operating system, and its two web requests: to GitHub, which looks for a newer nouez release,
and to Artificial Analysis, for model scores. The daemon also sends notifications and its own requests, which nouez
discards and this document leaves out. Message shapes are as captured in runs of nouez 0.12.4,
unless a section names a later version, with Claude Code
2.1.295 and Codex app-server daemon 0.162.0 (2.1.332 for the 2026-07-28 startup); client behaviour
described here (the discovery probe, progress tokens, the 120-second move to the background) was observed in those runs and is
not something nouez controls. Ids are invented, long objects are trimmed to the fields nouez
reads, and quoted error texts marked as excerpts are shortened.
\end{abstract}

\section{Overview}

Two coding agents look at a problem differently. nouez gives each a fixed role:
\ccname{} is the main developer and owns the work; \cxname{} is a consultant that Claude asks
for second opinions. Consultants that nouez starts run in a read-only sandbox, with none of the
user's MCP servers, Codex plugins or ChatGPT apps (Section~\ref{sec:resolve}), and
\code{StartConsultant} only ever reuses those. Claude can also message a Codex session the user
opened, by name and with \code{allow\_user\_session: true}, when the user asks; such a session
keeps the user's own permissions. Everything
happens from the single Claude Code terminal.

A message makes three hops (Figure~\ref{fig:components}):

\begin{enumerate}
  \item \textbf{Claude Code $\leftrightarrow$ nouez.} Claude Code starts \code{server.py} as a child
        process and speaks MCP to it: JSON-RPC~2.0, one JSON object per line on stdin/stdout.
  \item \textbf{nouez $\leftrightarrow$ Codex daemon.} A tool call that needs the daemon starts
        \code{codex app-server proxy} (once per call; the status screen keeps one open while it runs),
        which relays its stdio to the daemon's local control socket.
        Over that pipe nouez performs a WebSocket handshake and then exchanges JSON-RPC messages
        in WebSocket text frames.
  \item \textbf{nouez $\rightarrow$ operating system.} nouez opens no window for a consultant: the
        status screen's consultations page shows each one's latest turn, and gives the
        \code{codex resume <id>} a user can run to type to it. When a server starts, it closes the
        panes nouez 0.22.0 and earlier opened (Section~\ref{sec:old-panes}).
        The Claude Code session tools work only at this level: they open terminal windows
        running \code{claude}, read the files Claude Code keeps about its running sessions, and
        end processes.
\end{enumerate}

Three more tools serve a different purpose: they manage Claude Code sessions on the same computer,
so that a session driven from the Claude app with Remote Control can start another one in a
different project (\code{OpenClaudeSession}), see which are running (\code{ListClaudeSessions})
and end a stuck one (\code{CloseClaudeSession}). They don't involve Codex or talk to Claude Code;
they work through the operating system and the files Claude Code keeps
(Sections~\ref{sec:claude-tools} and~\ref{sec:claude-os}).

Those tools are what make the phone the main place to work. A \code{claude remote-control}
server is tied to the folder it runs in, so \code{server.py dispatcher} keeps one running in a
folder of its own, the dispatcher, from the user's sign-in on: a session the Claude app starts
there opens, lists and closes sessions in every project (Section~\ref{sec:dispatcher}).

\section{Inside the server}
\label{sec:inside}

\code{server.py} is a single file using only the Python standard library. One thread reads
stdin; every request runs on its own worker thread, because a tool call can block for minutes
while Codex works.

\code{route()} sorts each parsed line:

\begin{itemize}
  \item Not an object, an \code{id} that isn't a string or number (booleans included), or a
        request with \code{"id": null}: answer \code{-32600 Invalid Request} right away, from the
        read loop's thread.
  \item No \code{method}: it is Claude Code's answer to a request nouez sent (\code{roots/list}); wake the waiting thread. Answers nobody is waiting for are dropped.
  \item \code{notifications/cancelled}: set the Event of the named request, if it is still running. Malformed params are ignored.
  \item Anything else: register a cancel Event for \code{tools/call} before starting its worker
        thread, so a cancel that arrives while the worker starts up is not lost. (A cancel that
        arrives before its request has nothing to cancel and is ignored.)
\end{itemize}

Any exception inside \code{route()} is logged and the loop continues, so no single line can stop
the server. Inside the worker, \code{handle()} makes sure every request with an id gets a
response unless it was cancelled: if \code{dispatch()} raises, it answers
\code{-32603 Internal error: <exception>}. An exception inside a tool is different: it becomes an
\code{isError} result reading \emph{``Unexpected error: <exception>''}.

\section{Claude Code \texorpdfstring{$\leftrightarrow$}{<->} nouez (MCP)}
\label{sec:mcp}

\subsection{Startup}

Claude Code 2.1.332 first probes the 2026-07-28 protocol with \code{server/discover}. nouez
answers it, so Claude Code stays on 2026-07-28: there is no handshake, and every request carries
its version, capabilities and client in \code{\_meta}. nouez handles each such request on its own
and never sends that client a request, so it doesn't ask for roots: tools take \code{cwd}, which
defaults to the folder it started nouez in, and outside git a call's consultants are looked for in
the folder the call names, never in a workspace above it.

\begin{wire}[Claude Code $\rightarrow$ nouez: discovery]
{"jsonrpc": "2.0", "id": "server-discover-probe-1", "method": "server/discover", "params": {"_meta": {
  "io.modelcontextprotocol/protocolVersion": "2026-07-28",
  "io.modelcontextprotocol/clientInfo": {"name": "claude-code", "version": "2.1.332", ...},
  "io.modelcontextprotocol/clientCapabilities": {"roots": {"listChanged": true},
    "elicitation": {"form": {}, "url": {}}}}}}
\end{wire}
\begin{wire}[nouez $\rightarrow$ Claude Code]
{"jsonrpc": "2.0", "id": "server-discover-probe-1", "result": {"resultType": "complete",
  "supportedVersions": ["2026-07-28", "2025-11-25", "2025-06-18", "2025-03-26"],
  "capabilities": {"tools": {}}, "instructions": "Consultants are read-only second opinions ...",
  "ttlMs": 0, "cacheScope": "private",
  "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "nouez", "version": "0.31.2"}}}}
\end{wire}

Every 2026-07-28 result says \code{"resultType": "complete"} and names nouez in \code{\_meta};
\code{tools/list} adds \code{ttlMs} and \code{cacheScope}. A request whose version nouez doesn't
know gets \code{-32022} with \code{data.supported} and \code{data.requested}; one without
\code{clientCapabilities}, or carrying any of these \code{\_meta} keys without a version string,
gets \code{-32602}, so it never runs under the handshake's rules; \code{ping} and
\code{initialize} carrying the 2026-07-28 \code{\_meta} get \code{-32601}. An opt-in approval
(\code{NOUEZ\_ASK\_TRUST}, \code{NOUEZ\_ASK\_USER\_SESSION}) goes back as
\code{"resultType": "input\_required"}, with an \code{elicitation/create} request under
\code{inputRequests} and a single-use \code{requestState}. Claude Code shows the prompt and sends
the call again with \code{inputResponses}; nouez takes the answer only with a
\code{requestState} it issued for the same question and the same call (a SHA-256 of the tool's
name and all its arguments), once, within 10 minutes, and otherwise asks again. A client whose
\code{clientCapabilities} show no form elicitation (none at all, or \code{url} only) gets
\code{-32021} with \code{data.requiredCapabilities} instead of a prompt it can't show.

\subsection{Startup with the handshake}

A client that sends \code{initialize} first, such as a Claude Code from before 2026-07-28, gets the
legacy lifecycle, which lasts for the process. A request without the 2026-07-28 \code{\_meta} that
comes before any \code{initialize}, other than \code{ping} and \code{server/discover}, gets
\code{-32600}, so a client that skips the handshake never runs under its rules; \code{server/discover}
without that \code{\_meta} gets 2026-07-28's \code{-32602}.

\subsection{Tool calls and results}

In the captured runs, every \code{tools/call} from Claude Code 2.1.295 carried a progress token in
\code{\_meta}. Claude Code moved any call that ran past 120 seconds to the background, where its
result arrives later as a task notification.

While SendConsultantMessage or GetConsultantReply waits for a running turn, nouez answers a
progress token with \code{notifications/progress}: at most one every 10 seconds, with
\code{progress} counting up from 1 and no \code{total}, since a turn's length isn't known. The
message names the turn, the time waited so far and the latest line of output. None is sent once
the call is cancelled, and none without a token. In the runs before 0.4.0, Claude Code did not
display progress notifications.

\begin{wire}[nouez $\rightarrow$ Claude Code: progress while waiting]
{"jsonrpc": "2.0", "method": "notifications/progress", "params": {"progressToken": 14, "progress": 3,

Argument values are checked by the tool and reported as \code{isError} results:

`new` must be true or false, not 'yes'.

codex-nouez-77c2e0 is a Codex session the user opened, not a read-only consultant: it keeps the user's own permissions and may be able to edit files. Nothing was sent. Only if the user asked you to message this session, send again with allow_user_session=true; otherwise use StartConsultant.

\subsection{Running as a plugin}
\label{sec:plugin}

Installed as a Claude Code plugin, nouez starts as \code{py -3 -I launch.py DATA}, DATA being the
plugin's data folder (\code{CLAUDE\_PLUGIN\_DATA}, \code{\textasciitilde/.claude/plugins/data/nouez-MARKET}).
\code{launch.py}, standard library only, copies the plugin's \code{server.py} to
\code{DATA/app/server.py} under a lock, only when its \code{SERVER\_VERSION} is higher (with
\code{-{}-plugin-dir}, whose data folder ends in \code{-inline}, also when the same version has
other bytes), and writes \code{app/plugin.json} with the plugin's id. It does so at its start,
so a newer copy is put in place when a session starts nouez from the updated plugin (a new session,
or \code{/reload-plugins}). A DATA or \code{app} folder that is a link is refused: the launcher
ends without writing or running anything. By that file
\code{server.py} knows it runs as the plugin: its tools are then
\code{mcp\_\_plugin\_nouez\_consultants\_\_NAME}, its allow rules and doctor say so, and it warns
when a clone is registered as well. The launcher runs that copy as its child and passes each line
on unchanged, with these exceptions:
\begin{itemize}
  \item The answer to the first \code{initialize} gains \code{"tools": \{"listChanged": true\}}.
  \item A request of the child's to Claude Code (\code{roots/list}, a prompt) goes out as
    \code{launchG-ID}, G counting the children, and its answer goes back under the child's id;
    an answer for a child that has ended goes nowhere.
  \item Before passing on a request when the copy on disk is newer than the child's (its size and
    time looked at), the launcher asks the child \code{nouez/idle} and holds Claude Code's
    requests until the answer, for at most 15 s (none counts as not idle). The child is idle when
    nothing a new process wouldn't know about is under way: no request or notification being
    handled, no request to Claude Code open, no tool call running, no prompt waiting, no provider
    the user named still waiting for its message, no trust report or home-folder warning it gave
    still waiting for the user's answer (15 min at most), no usage-log write, and no Codex turn it started
    or steered still running (asked of the daemon, which nouez doesn't start for this).
\end{itemize}

\begin{wire}[launch.py $\rightarrow$ nouez, and back]
{"jsonrpc": "2.0", "id": "launch-idle-3", "method": "nouez/idle"}
{"jsonrpc": "2.0", "id": "launch-idle-3", "result": {"idle": false, "why": "a tool call is running"}}
\end{wire}

When the child is idle, the launcher closes its input, gives it 10 s to end (then ends it), starts
the newer copy, and gives it the session's \code{initialize} again (its answer isn't passed on)
and \code{notifications/initialized}, then the requests it held, and sends Claude Code
\code{notifications/tools/list\_changed}. If the new copy refuses that \code{initialize} or
doesn't answer within 30 s, each held request gets error \code{-32603} saying to reconnect nouez
with \code{/mcp}, and the launcher ends the copy and itself. Nothing is handed over: no consultation, prompt or
request is under way to hand. A 2026-07-28 client has no \code{initialize} to give again: each
request carries what it would, and \code{tools/list} answers with \code{ttlMs} 0. When the child
isn't idle, the held requests go to it and it is asked again 10 s later; one from before 0.30
answers \code{-32601} and is never asked again, so its session keeps it until it ends. A
\code{notifications/cancelled} for a held request drops it, never sent.

The plugin's \code{PreToolUse} hook on \code{NouezSettings} runs \code{server.py guard} with the
hook's input. For a call that turns one of the four protections on or off, it answers
\code{"permissionDecision": "ask"} in the \code{default}, \code{acceptEdits} and \code{auto} modes
and records an approval slot in \code{DATA/approvals.json} (the change, the Claude Code process
running the session as its id and start time, and when); in any other mode, or when it can't find
that process, it answers \code{"deny"}. Claude Code shows its own prompt, on the phone too, and runs
the tool only on a yes. \code{NouezSettings} then takes the matching slot, once; one older than 10
minutes is gone. Any other call, a hook that fails among them, is left to Claude Code's own rules,
and then \code{NouezSettings} refuses a protection, finding no slot.

\begin{wire}[server.py guard $\rightarrow$ Claude Code]
{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "ask",
  "permissionDecisionReason": "nouez: turn the protection ask_trust off?"}}
\end{wire}

\subsection{Connecting}

A tool call that gets past argument checks opens a fresh \code{CodexClient} and closes it in a
\code{finally} block, killing the proxy's process tree. The status screen's consultations page
keeps one open in a thread of its own while the screen runs, and opens another after it fails. The
connection has four steps:

If the proxy closes its output before answering, no daemon is listening (it does not survive a
restart of the computer). nouez then runs \code{codex app-server daemon start} once, without
pipes and waiting at most 30 seconds for the command, and retries the connection every half
second for up to 20 seconds. On Windows, when \code{MSYSTEM} says nouez runs under Git Bash (the
waiter runs in Claude Code's Bash tool), the command gets the environment without \code{MSYSTEM},
\code{SHELL} and \code{EXEPATH}, and without the \code{PATH} folders that hold \code{msys-2.0.dll}.
The daemon and its updater inherit that environment, and the update script's bare \code{tar} would
otherwise find GNU tar, which reads \code{C:} as a remote host. Only if that fails does it report \emph{``Codex app-server daemon is
not reachable, and starting it did not help. Run `codex app-server daemon start` in a terminal to
see why, or open a Codex session.''} If the proxy
says nothing within 15 seconds, \emph{``Codex app-server proxy did not respond within 15s.''}; for
any status other than 101, \emph{``WebSocket upgrade refused: <first 200 bytes of the header>''}.

\subsection{Frames}

\begin{center}\small
\begin{tabular}{@{}l l l@{}}
\toprule
\textbf{Opcode} & \textbf{Meaning} & \textbf{nouez does} \\
\midrule
\code{0x1} text, \code{0x0} continuation & a JSON message, possibly split & reassemble until FIN, then parse \\
\code{0x9} ping & keep-alive from the daemon & answer with \code{0xA} pong, same payload \\
\code{0x8} close & daemon is closing & stop reading; pending requests fail \\
\bottomrule
\end{tabular}
\end{center}

Frames nouez sends are masked, as RFC 6455 requires of clients: text frames for its messages and
pong frames for the daemon's pings. A received message over 64~MiB ends the connection. A reader
thread puts parsed messages on a queue; \code{request()} sends one message and waits up to 15
seconds for the response with the same \code{id}. Everything else the daemon sends meanwhile,
notifications and the daemon's own requests alike, is discarded. A consultant never waits on
those requests, because it was started with \code{approvalPolicy: "never"}.

\subsection{Message format}

The daemon speaks JSON-RPC without the \code{"jsonrpc"} member. Ids are integers counting from 1
on each connection.

\begin{wire}[nouez $\rightarrow$ daemon]
{"id": 1, "method": "initialize", "params": {"clientInfo": {"name": "nouez", "version": "0.12.4"}}}
\end{wire}
\begin{wire}[daemon $\rightarrow$ nouez]
{"id": 1, "result": {
  "userAgent": "codex-tui/0.162.0 (Windows 10.0.26200; x86_64) WindowsTerminal (nouez; 0.12.4)",
  "codexHome": "C:\\Users\\you\\.codex",
  "platformFamily": "windows", "platformOs": "windows"}}
\end{wire}
\begin{wire}[nouez $\rightarrow$ daemon]
{"method": "initialized"}
\end{wire}
\begin{wire}[daemon $\rightarrow$ nouez: an error response]
{"id": 7, "error": {"code": -32600, "message": "thread 01a1f3c2-... is not materialized yet"}}
\end{wire}

nouez turns an error response into \emph{``\textless method\textgreater{} failed: \textless message\textgreater''}. A few
messages mean ``this session has no history yet'' and are treated as an empty turn list rather
than a failure: \code{not materialized}, \code{missing source rollout}, \code{no rollout found},
\code{is empty}, \code{list\_turns is not supported yet}.

\subsection{Data shapes}

\begin{wire}[A thread (session), fields nouez reads; the daemon sends about 30]
{"id": "01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17",
 "cwd": "C:\\Users\\you\\Projects\\nouez",
 "model": "gpt-5.6-sol", "modelProvider": "openai",
 "status": {"type": "idle"},             // "idle" | "active" (+ "activeFlags") | "notLoaded" | "systemError"
 "threadSource": "nouez",                // null for sessions the user opened
 "ephemeral": false, "parentThreadId": null,
 "name": "Diff review", "updatedAt": 1791547200}
\end{wire}

The consultant's name is derived, not stored: \code{codex-} + the last folder of \code{cwd} +
\code{-} + the last six characters of the id, lower-cased: \code{codex-nouez-4d9f17}.

\begin{wire}[A turn, fields nouez reads]
{"id": "01a1f3c4-8b20-7d55-b1e3-6a9c0f2e7d31",
 "status": "completed",                  // "inProgress" | "completed" | "interrupted" | "failed"
 "error": null,                          // may be {"message": "..."} when failed or interrupted
 "rootTurnId": "01a1f3c4-8b20-7d55-b1e3-6a9c0f2e7d31",  // its own id, or the turn it carries on
 "items": [
   {"type": "userMessage", "content": [{"type": "text",
     "text": "[Message from Claude Code via the consultants bridge]\n\nReview this diff ..."}]},
   {"type": "agentMessage", "phase": "commentary", "text": "Reading server.py ..."},
   {"type": "agentMessage", "phase": "final_answer", "text": "Two issues. 1) ..."}]}
\end{wire}

\code{phase} is \code{"commentary"} for progress messages, \code{"final\_answer"} for the answer,
or \code{null}. For a turn that has ended, the reply is the text of all \code{agentMessage} items
with \code{phase: "final\_answer"}, or, if there are none, of the last \code{agentMessage}. For a
turn still running, nouez shows the \emph{output so far} instead: every \code{agentMessage}
after the turn's latest \code{userMessage}, whatever its phase, keeping the last 4,000
characters. A steered message adds a \code{userMessage} to the running turn, so output written
before it arrived is not shown as if it answered it. This is the snapshot from the latest poll;
nouez polls instead of following streamed events, so it may lag the session by one poll.

\code{rootTurnId} names the first turn of the chain of work that led to a turn, the turn's own id
for a turn that starts one. It shows ancestry, not by itself continuation: a client may start new
work on behalf of an earlier turn. Codex uses it when a restarted daemon reloads a session whose
turn the restart cut off: the old turn ends \code{interrupted}, with no timestamps, and the
daemon's next turn there, started with no \code{userMessage}, goes on with the work and names the
old turn as its root. On 2026-11-19 Codex's scheduled daemon update (0.170.0 to 0.171.0) did this,
about 8 seconds after it stopped the old daemon. nouez takes a turn as the continuation of an
interrupted turn, on the strength of its root alone, only if it is the next turn in the thread,
holds no message, and its root is the interrupted turn, or that turn's own root when the
interrupted turn is itself a continuation; a turn with a message of its own, or a later one that
only shares the root, is not taken. (A send also follows a turn that holds its own text.) A
continuation a message steered later is not recognised from the interrupted turn any more, but a
waiter that already followed it keeps it. It follows such chains wherever it waits for or reads a turn, and
the history names a turn with no message as Codex's, not as someone's empty message. nouez never
sends a continuation, so it can't refuse one.

\subsection{Finding a session}
\label{sec:resolve}

A \code{to} that is a full thread id is read directly with one \code{thread/read}, plus
\code{thread/loaded/list} to know whether it is loaded. Every other \code{to} first lists
sessions, then matches. Listing reads each loaded session, and each unloaded one that Codex says
nouez started, because \code{thread/list} omits \code{threadSource}:

\begin{wire}[1. Sessions loaded in the daemon (paged)]
-> {"id": 2, "method": "thread/loaded/list", "params": {}}
<- {"id": 2, "result": {"data": ["01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17", "01a1e8a0-..."], "nextCursor": null}}
\end{wire}
\begin{wire}[2. Read each loaded session]
-> {"id": 3, "method": "thread/read", "params": {"threadId": "01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17"}}
<- {"id": 3, "result": {"thread": {"id": "01a1f3c2-...", "cwd": "C:\\Users\\you\\Projects\\nouez", "threadSource": "nouez", "status": {"type": "idle"}, ...}}}
\end{wire}
\begin{wire}[3. Codex's index of saved sessions, 100 a page, to find consultants the daemon has unloaded]
-> {"id": 5, "method": "thread/list", "params": {"limit": 100, "useStateDbOnly": true}}
<- {"id": 5, "result": {"data": [{"id": "01a1d9b7-...", "originator": "nouez", "cwd": "...", ...}, ...], "nextCursor": "100"}}
-> {"id": 6, "method": "thread/read", "params": {"threadId": "01a1d9b7-..."}}     // kept only if threadSource == "nouez"
\end{wire}

Codex records, as each session's \code{originator}, the \code{clientInfo} name of the client that
started it (\code{CLIENT\_NAME}, \code{"nouez"}; \code{"codex-tui"} for the user's own), so only
the sessions nouez started are read, and those outside the project when one is asked for are
skipped. Pages follow \code{nextCursor}, \code{SAVED\_PAGES} (20) at most, 2,000 sessions not
archived; a cursor that comes back again ends them. The usage log plays no part, so consultants are
found the same with it off. A Codex that refuses \code{useStateDbOnly}, or whose index returns
nothing, gets one \code{thread/list} of 50 without it, as Codex finds sessions on disk; one whose
summaries have no \code{originator} gets one page, its first 50 read. When the index holds no
session that \code{to} could name (a name keeps the id's last six characters, so only those are
read), the lookup is made once more on disk, for sessions copied from another computer without
Codex's index; so is \code{StartConsultant}'s and \code{ListConsultants}'s when they find none of
nouez's consultants. A later page that fails is an error, never a shorter list, so a consultant on
page two is not taken for missing and a second one started. Then \code{to} is matched, case-insensitively: an exact name or id first; otherwise a
unique id prefix or suffix (except for \code{StopConsultant}, which accepts only exact matches);
otherwise a direct \code{thread/read} of \code{to} as a full id, which reaches older consultants.
A name keeps only the id's last six characters, so two sessions can share one; such a name is

\subsection{StartConsultant}

Gets the consultant for a project. It reuses the most recently used session that nouez
started in the project (its git work tree; outside git, the exact folder \code{cwd} names, so a

A notice that a newer nouez is out comes before the Codex one. When Claude Code sends
\code{initialize}, nouez starts a background thread that looks up the latest release, so no tool
call waits for it. The thread first reads \code{nouez/latest-release.json} in the user's cache
folder (\code{\%LOCALAPPDATA\%} on Windows, \code{\$XDG\_CACHE\_HOME} or
\code{\textasciitilde/.cache} elsewhere). An answer less than a day old is used as it is, and so
is a failed attempt less than an hour old, which gives no notice. Otherwise nouez asks GitHub through \code{fetch\_json}, the one function that makes nouez's
web requests (it starts only at \code{RELEASES\_URL} and \code{AA\_MODELS\_URL}, refuses a redirect
to another scheme, host or port, so the Artificial Analysis key can't follow one, and reads at
most a set size),
with no credentials and a 3-second timeout on each network step (not a deadline for the whole
request: name lookup and several slow reads can take longer), and saves the result, a failure
included, through a temporary file of its own (\code{mkstemp}) and \code{os.replace}, so servers
starting together don't write into one file. Servers that start at the same moment may each ask.
GitHub sees the request's IP address and time and the version in \code{User-Agent}; the request
goes through any proxy set in the environment. A cache file over 4~KB, or one whose fields aren't a
finite time and a version of at most six digits per part, is ignored. A thread that can't start, or
any error in the check or the notice, leaves the \code{initialize} answer and the consultation as
they are. Setting \code{NOUEZ\_NO\_UPDATE\_CHECK=1} turns the lookup off.
\begin{plain}[nouez to GitHub (HTTPS)]
GET https://api.github.com/repos/jibarix/nouez/releases/latest
Accept: application/vnd.github+json
User-Agent: nouez/0.12.4

200 {"tag_name": "v0.13.0", ...}             (drafts and pre-releases are never "latest")
\end{plain}
nouez keeps the version only if the tag reads \code{v}$n.n.n$; anything else, and any failure
(offline, a proxy, a rate limit), means no notice. The notice appears once per release in each
server process, only for a version newer than the running one. In the phone dispatcher, whose
supervisor marks its \code{claude} with \code{NOUEZ\_DISPATCHER=1} (a session it opens doesn't get
the mark), the dispatcher's own tools carry the notice instead, each call there may look again an
hour after the last lookup, and the notice tells Claude to run nothing: the update takes the
computer, then \code{dispatcher install} again. The command it gives uses the folder
\code{server.py} runs from, in single quotes, which PowerShell and POSIX shells read literally,
so a folder name like \code{\$(...)} can't run anything. A folder whose name has a \code{'} or a
control character gets no command: Claude is told to ask the user to run the pull. If the folder
isn't a git checkout, the notice points to the release page instead. Either way, Claude asks the
user to reconnect only after the update worked:
\begin{plain}[Result text: nouez update notice]
nouez 0.13.0 is out; this server is 0.12.4. What changed: https://github.com/jibarix/nouez/releases/tag/v0.13.0. Tell the user and go ahead with the consultation. Only if the user asks you to update, run `git -C 'C:/Users/you/nouez' pull --ff-only` in a shell. If git fails (local changes, a conflict, no branch checked out), stop there: tell the user what git said, don't ask them to reconnect, and don't discard, stash or switch anything without the user's say. Only after the pull succeeds, ask the user to run /mcp and reconnect consultants, which loads the new version; the Codex consultants keep their sessions.
\end{plain}

\subsection{SendConsultantMessage}
\label{sec:send}

The central tool. A lock per session, held only inside this nouez process, makes sure two of its
concurrent sends can't both start a turn; it does not cover other clients of the daemon, such as
the user typing in a Codex terminal. The lock is held through delivery and the check that the new
turn is listed, and is released before the long wait, so a slow reply
doesn't block other senders.

Two options add to the text, and only when passed. \code{owner\_words} is the user's own words,
quoted as they typed them; they go first, marked off, and the rest is labelled as the sender's, so
the consultant can tell the request from Claude's reading of it. \code{revision: true} adds a line
after the header with the git commit, branch and number of uncommitted paths in the consultant's
folder (from \code{git rev-parse} and \code{git status -{}-porcelain}, run by nouez with a timeout)
and asks the consultant to name that revision in its answer. Outside git the line says so.
History finds the line by its fixed start and end, so a branch name or path with \code{]} in it
doesn't stop it being hidden.

With uncommitted changes, nouez also takes their diff then, from the top of the repo even when the
consultant's folder is a subfolder. Git writes all of it, so names, file modes, line endings and
bytes that aren't UTF-8 come out as \code{git apply} expects: nouez copies git's index to a temporary
folder, adds the untracked files that \code{git ls-files -{}-others -{}-exclude-standard} lists to
the copy as intent-to-add (\code{git add -N}), and runs \code{git diff} against the commit the line
names, with that copy as \code{GIT\_INDEX\_FILE}, so nothing in the repo is written. Every git
command runs with \code{-{}-no-optional-locks}, no hooks (\code{core.hooksPath=/dev/null}) and no
fsmonitor, and \code{git status} and \code{git diff} with options that override the user's settings
that would hide untracked files, change the names' prefixes or summarise submodules. It leaves out an untracked file with a part
of its path that looks like a secret (\code{.env}, \code{.netrc}, \code{id\_rsa}, \code{*.pem},
\code{*.key}, \code{settings.local.json}, or a name with \code{secret}, \code{credential},
\code{token} or \code{password}), one over 256\,KB, a repository inside this one, and any past the
first 200; from git's diff, it leaves out binary files and submodules with changes inside, and
names up to five of these in the line and counts the rest. A diff, or \code{git status} or
\code{ls-files} output, over 8\,MB isn't taken. When a git command fails,
times out or the diff can't be saved, the line says so, names no digest and asks the consultant
to review the working tree instead. The diff is saved as
\code{patches/<digest>.patch} in nouez's cache folder, where \textit{digest} is the first 16 hex
digits of its SHA-256; the line names the file and the digest and asks the consultant to review
that diff rather than the working tree, which may change while it reads, and to name the digest
in its answer. The same changes give the same digest, so two consultants' verdicts can be checked
to be about the same input. Saved diffs older than 14 days are removed when another is saved and when a server starts.
git runs with \code{GIT\_NO\_LAZY\_FETCH=1} and \code{-{}-no-lazy-fetch}, so a partial clone's
missing objects aren't fetched. A git older than 2.45 refuses that option; with one, nouez takes no
diff of a repository with \code{extensions.partialClone} or a \code{remote.}\textit{name}\code{.promisor}
set, or whose settings \code{git config -{}-list} can't read: the line asks the consultant to review
the working tree. Clean filters the repository configures still run. The
usage log records only the digest (\code{patch}). A Codex consultant reads the file itself, and
nouez takes the diff only after checking that the session is one it may message. An Antigravity
consultant runs no commands and may not be allowed to read nouez's folder, so its message carries
the diff, before the bridge header, where \code{GetConsultantHistory} doesn't show it; the message
stays in the consultant's records like any other, and goes to Google. With
\code{attach\_diff} false nouez takes no diff for it, and the line gives only the commit, branch and
count; that is refused for a blind second opinion on a review that named a revision, which must see
the same diff. A diff over 200{,}000 bytes, or with bytes that aren't
UTF-8 (which the message couldn't carry unchanged), isn't attached: the line gives its size and asks
for a review of the working tree.

\code{model} and \code{effort} change the consultant's Codex model or reasoning effort without
starting a new session, so it keeps its context. nouez refuses only an empty value, blanks and control
characters (provider ids such as \code{gpt-oss:20b} pass) and leaves Codex to reject one the model
doesn't support. They
go into \code{turn/start}, and Codex keeps them for the session's later turns as well, so the result
says the setting stays until changed, after a quick reply too. A running turn can't change them:
when nouez sees the session busy, a send with either is refused and nothing is sent, rather than
steering the turn with them silently dropped; a value the running turn already has doesn't count,
since \code{ConsultantBudget}'s suggestion is passed with every message. Like the choice between start and steer, this check
is not atomic: a turn another client starts between it and \code{turn/start} is not seen.

Before either check, a message this server already delivered to the running turn is not sent
again: the result says it was already in the running turn and gives that turn's id, and with

what Claude meets when it sends again after its context was summarised and it lost track of a
send. Only nouez's own record counts (\code{\_delivered}: each turn's texts, header included, added
once \code{turn/start} or \code{turn/steer} returns), as for steering: \code{thread/turns/list}
gives a summary of a turn's items, its first user message and last agent message, so a steer
doesn't show there, and the same text typed in \code{codex resume} is not a message this server delivered. A
send whose acknowledgement was lost is not in the record, and after a restart the record is empty.
Nothing goes to the daemon and no \code{send} event is logged. A message sent again after the turn
ended starts a new turn as usual, since the work under review may have changed.

\subsection{GetConsultantReply}

Reads a reply without sending anything. A send returns after 5 seconds by default, usually before
the reply is ready, and Claude is told not to wait for it but to run the waiter (next section) in
the background. Without background commands, it calls this tool with the returned
\code{turn\_id} when the user asks or when it next needs the reply, and the call returns at once.
When the user does want Claude to wait, it passes \code{wait: "done"}. That call returns when the turn ends, when an error occurs (such as a
lost daemon connection), or after the 4-hour cap, so a client that moved it to the background is
notified when the reply is ready, up to one 1.5-second poll late. An error or the cap is not a
reply; call again.

\subsection{The waiter command}

\code{server.py wait <thread\_id> <turn\_id>} is not a tool but a command line. A send that
returns before the reply, and a \code{GetConsultantReply} that finds the turn still working, give
it with full paths (\code{sys.executable -I} and the absolute path of \code{server.py}) and tell
Claude to run it as a background command. In Claude Code that is the Bash or PowerShell tool with
\code{run\_in\_background}: Claude is free at once, and when the command exits Claude Code wakes it
with the command's output, so the reply arrives without the user asking for it. A path made only
of letters, digits and \code{./:+-} is left bare, so the command runs as is in either shell and a
permission rule can match it by prefix (backslashes are written as \code{/} on Windows). Any other
path is quoted for each shell: in double quotes when it holds none of \code{\$`"!} or curly
quotes, otherwise in single quotes, with a \code{'} written \code{'\textbackslash'{}'} for Bash and
doubled for PowerShell. When the two forms differ, the result gives both, the PowerShell one after
\code{\&}. A path with a control character gets no command: Claude is told to use
\code{GetConsultantReply} instead.

\code{server.py allow-rule} prints those rules for the interpreter that runs it, one per shell tool
(the PowerShell one only on Windows):
\begin{plain}
Add these to permissions.allow in ~/.claude/settings.json:
"Bash(C:/Python313/python.exe -I C:/Users/you/nouez/server.py wait *)",
"PowerShell(C:/Python313/python.exe -I C:/Users/you/nouez/server.py wait *)"
\end{plain}
They name one interpreter and one script, so Claude Code keeps them in auto mode, which drops only
broad interpreter rules; without them it asks before each waiter, or auto mode may block it.

The waiter opens its own connection, resolves the thread by exact id, and looks for the turn among
its \code{REPLY\_LOOKBACK} (100) most recent turns. A turn that is missing ends it with exit
code~1. An interrupted turn that Codex carried on is replaced by the last turn of its chain. A
turn that has already ended is printed at once; a running one, which is always among the newest,
and an interrupted one that Codex may yet carry on (as a send waits for one), are polled with
\code{wait\_for\_turn} for up to \code{WAITER\_SECONDS} (25 minutes). That is how the waiter
outlives a daemon restart: the restart breaks its connection and ends the turn
\code{interrupted}, the waiter reconnects, and it follows the continuation the new daemon starts.
A continuation followed during the wait is kept across a dropped connection, so the waiter
reconnects to it even after the turn it started with has left the newest 100.
Claude Code stops a background command after 30 minutes by default, so at that point the waiter
exits with code~0 and the \emph{still working} result, including the output so far and the same
command to run again; Claude starts a new waiter. It exits the same way, early, when the turn has
shown nothing new for \code{STALL\_SECONDS} (10 minutes), with \emph{``nouez has seen no change
from \ldots\ for 10 minutes: it may be stuck, or still thinking or running a long command. Tell the
user.''}\ in place of the 25-minute note; for a Codex session the user opened, which
\code{StopConsultant} refuses, it says to stop it from its terminal. \code{StallWatch}, passed as
the \code{on\_poll} of \code{wait\_for\_turn} or \code{agy\_wait}, compares each snapshot of the
running turn with the one before. For Codex that is the size of the session's rollout file (the
thread's \code{path}), with the turn's items: the items alone are the summary above, which commands
and reasoning leave unchanged, while Codex writes the rollout at least every minute or so during a
turn (47 seconds at most across a month of turns on one machine). For agy it is the size of the turn's
\code{.jsonl} file, to which agy adds an event every few seconds while it works (a 3-minute Neon
turn wrote 431). A single command that runs quietly past the limit looks stuck too, hence the
wording. The watch is kept across a
dropped connection, so reconnecting is not taken for progress, and a followed continuation counts
as a change. When the turn ends, the waiter prints
\emph{``The consultant's turn has ended (thread \ldots, turn \ldots).''} and the turn formatted as
\code{GetConsultantReply} would, with the reply cut at \code{WAITER\_REPLY\_CHARS} (20,000)
characters and the rest saved to a file, and exits with code~0. Its standard output is UTF-8.
After the reply it says when it followed a continuation (\emph{``Turn \ldots\ was interrupted and
Codex carried it on as turn \ldots, whose reply is above.''}), when the daemon's version changed
during the wait (\emph{``The Codex daemon changed version during the wait (0.170.0 -> 0.171.0): it
was updated and restarted, which interrupts running turns.''}), or else when a connection dropped.

A failed connection (\code{BridgeError}, or an \code{OSError} such as a broken pipe) is retried
10 seconds later, never past the 25-minute deadline. After \code{WAITER\_RETRIES} (3) failures in a
row, a count that each working connection resets, it prints \emph{``Stopped waiting for turn
\ldots''} with a pointer to \code{GetConsultantReply} and exits with code~1. The waiter dies with
the Claude Code session that started it; the reply stays readable with \code{GetConsultantReply}.

\subsection{ConsultantBudget}
\label{sec:budget}

\code{ConsultantBudget} gathers the facts for choosing a consultant's model and effort, and changes
nothing, except that a \code{kind} with a \code{provider} keeps nouez's pick for the next send of
that kind to that provider on its models (see the
\href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-named-provider}{lifetime and scope of a named provider}). It makes two requests to the Codex daemon, reads one file the user's status line saves, and
asks Artificial Analysis for model scores about once a week. Each part fails on its own: an
unreachable daemon or a missing file is reported in its place, and the rest still shows.

nouez reads these fields:

\begin{itemize}
\item \code{rateLimits}: \code{planType}; and for each of \code{primary} and \code{secondary}, its
  \code{usedPercent}, \code{windowDurationMins} and \code{resetsAt}.
\item \code{rateLimitResetCredits}: \code{availableCount}.
\item \code{model/list}: each model that isn't \code{hidden}, with its supported efforts
  (\code{supportedReasoningEfforts}).
\end{itemize}

A window whose numbers are missing, or whose reset is past, is left out. The pace is the rate of
use so far: the percentage used, divided by the time gone since the window started. It is shown
once 5\% of the window has gone. In a week's first 16 hours the time gone counts as 16 hours, so a
morning's use is spread over the night that follows it rather than projected through every night of
the week (7.8\% after 12\,h 30\,min is about 84\% by the reset, where the time gone alone gives
about 105\%); such a pace is called a first-day estimate wherever it is shown.

Claude Code tells only its status line command how much of its usage windows is used
(\code{rate\_limits.five\_hour} and \code{seven\_day}, each \code{used\_percentage} and
\code{resets\_at}). \code{server.py statusline}, set as (or called from) the status line command,
reads that JSON on stdin and saves the windows to \code{claude-usage.json}, each with the time it
was seen. Under a lock on \code{claude-usage.json.lock} it merges them with the saved ones: a later
window replaces an earlier one, the same window keeps the higher percentage, and a window that has
reset is dropped. It writes atomically, prints a short status line (nothing with \code{-{}-quiet}),
and exits 0 whatever happens, so it can't break the status line. The server only reads the file.
When Claude Code's own \code{settings.json} has no \code{statusLine}, a \code{dispatcher setup} that
went well, and isn't a dry run, offers nouez's (\code{statusline\_offer}): it asks when stdin and
stdout are a terminal and adds it only on a yes, or with \code{-{}-statusline}, after a checked copy
of the file, the other settings kept; elsewhere it says how. One of the user's own is kept, with the
\code{-{}-quiet} command to pass its input on.

\code{pagination.has\_more} is true. nouez keeps each model's name, maker, release date,
\code{artificial\_analysis\_intelligence\_index}, input and output price per million tokens, and
output speed, and shows the top 8 by index for OpenAI, Google and Anthropic.

\code{docs/consultants.md} dates the benchmark rationale.

\begin{itemize}
\item Walk the options in order, skipping providers that are absent. Resolve each model and effort
  against that provider's catalogue. Family matching compares names with the version numbers
  removed, then orders matches by version. Try another listed pick for that provider before
  using its default. A substitution within a model family, a switch to the provider default
  for a missing model, or a change to an unavailable effort adds a note. Skipping a missing
  model in favor of another listed pick can be silent. See the
  \href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-catalogue-fallback}{model and effort fallbacks}.
  Apply the named-provider restriction and exclude Claude models for work that requires an
  \href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-independent-review}{independent reviewer},
  including any send with \code{revision: true}.
\item Read the windows for the quota each remaining option spends. For Antigravity the
  \code{/usage} group lists identify the quota. Classify each option from those windows and
  discard blocked options: a window used up, or a limit reached. A window on pace to run out
  before its reset is not a block; a week on that pace counts as tight. An old reading gives a lower bound on use. An Antigravity turn that
  failed on its quota marks its group used up until the reset it named
  (\href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-quota-hit}{quota failures}). The
  \href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-usage-forecast}{forecast rule}
  specifies when a reading supports a pace.
\item Start with the first remaining option and compare options on other quotas. An option whose
  usage is unknown yields to known room, after the spare-week and pace comparisons below. A tight week can move the choice or lower its effort.
  A busy week can yield to spare quota except for a fact check. For eligible research and quick
  checks, compare spare weeks by reset time, keeping the first choice on a tie, then consider
  how far a week is behind pace if the earlier rules left the pick in place. See the
  \href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-tight-week}{tight-week rule},
  \href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-spare-week}{spare-week rule}
  and \href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-behind-pace}{final pace comparison}.
\end{itemize}

The same judgment of each window serves the send, the prompt hook and the status screen. At send, a
new Codex turn is refused, with nothing sent, only when Codex reports its limit reached and no
credits, read with one request on the connection already open, whether nouez picked the model or
Claude named it; the refusal names another quota with room, from readings already kept, or says why none
can be named. Antigravity never says whether AI credits can be spent, so a used-up group there only
adds a \code{(Usage: ...)} note naming where later turns can go; a forecast that a window runs out
adds nothing. A message added to a running turn is never refused for its usage and reads no usage before it
goes; which turns take one is the steering rule above.

With no option left, the text says to skip the consultation and tell the user why. For an
Antigravity choice, \code{StartConsultant}'s part names the model and level as well, since a new
Antigravity consultant checks its starting model before the first message can change it. The lines after
the choice carry the kind's notes (rounds of a review, the premise question of a critique, sources
for a fact check), the blind second opinion with the other provider's own suggestion when it has room, the subjects
Gemini~4 Neon scores best on when Neon is listed, its group has room and the choice isn't already
a Gemini model, and that a reused consultant keeps its last model and effort. The hand-out line can recommend sending code to write as kind \code{draft}; Claude checks and
applies the returned text locally. Research advice can name a second provider for reading a
page. See the \href{https://github.com/jibarix/nouez/blob/v0.31.2/docs/rules.md#rule-research-and-drafts}{research and draft advice}.
\code{tests/consult\_eval.py} checks in fresh \code{claude -p} sessions that Claude calls it and
follows it.

\subsection{Usage log and status screen}
\label{sec:usage}

nouez appends one JSON line per event to \code{usage-log.jsonl} in its cache folder and never lets
a failure there fail the tool call (it is written to stderr instead). Every server takes
\code{usage-log.jsonl.lock} from the rename check to the end of the append, so no line goes to a
file another server is renaming or deleting; an event that waits more than 2 seconds for it is
skipped, and so is one for a log that isn't a regular file (checked before and after the open,
which doesn't wait on a pipe). The file is renamed \code{usage-log-}\textit{date}\code{.jsonl} once it passes 20\,MB or
its first event is 30 days old, with a unique name (none, and no rename, if all are taken).
Renamed logs not changed for 365 days are deleted, then the oldest while the rest add up to more
than 100\,MB, under the same lock, when a server starts and on each write. Nothing is read,
written, renamed or locked through a link.
\code{NOUEZ\_NO\_USAGE\_LOG=1} turns it off; the unit tests and the live checks set it.

\begin{itemize}
\item \code{start}: \code{consultant}, \code{thread}, \code{new}, \code{project} (the folder's
  name) and \code{model}.
\item \code{send}: \code{consultant}, \code{thread}, \code{turn}, \code{project}, \code{mode}
  (\code{new} or \code{steer}), \code{model} and \code{effort} in effect, \code{changed} (those of
  the two the message changed), \code{kind}, \code{reason}, \code{chars}, \code{owner\_words},
  \code{patch} (the digest of the diff that \code{revision} took), \code{user\_session}, and
  \code{usage}: each window's percentage used on Codex (from
  \code{account/rateLimits/read}), Claude Code (from \code{claude-usage.json}) and, for an
  Antigravity consultant, each quota group, with \code{usage\_meta} holding the same keys, each
  window's \code{resets\_at} and \code{sampled} (when it was read; for Antigravity, when \code{agy}
  answered, even for an answer reused from its 90-second cache).
\item \code{reply}: \code{consultant}, \code{thread}, \code{turn}, \code{status}, \code{ms},
  \code{chars} and \code{verdict}. It is written when a waiting send, the waiter or
  \code{GetConsultantReply} sees the turn end, so a turn can have more than one; readers keep one
  per turn.
\end{itemize}

Every line also has \code{ts} (Unix seconds). No line holds the text of a message or reply.
\code{kind} and \code{reason} are \code{SendConsultantMessage} arguments; an unknown \code{kind}
is refused before anything is sent. A turn that failed or was interrupted has the verdict
\code{incomplete}; the status screen applies that rule to replies logged by older versions too.
Otherwise the verdict is read from the first line of the reply that isn't blank. A line that starts
with a verdict label (``Verdict:'', ``**Final verdict** -'', after any numbering or formatting) is
read from the word after it: ``yes, with changes'' and the like are \code{changes}; ``no changes''
or ``no blockers'' is \code{yes}; ``incomplete'', ``inconclusive'' or ``not reviewed'' is
\code{incomplete}; ``changes'' is \code{changes}; ``no'', ``no-go'', ``not approved'', ``reject''
or ``blocked'' is \code{no}; ``yes'', ``go'', ``approved'', ``LGTM'', ``ready'' or ``OK'' is
\code{yes}. So a caveat later in the line doesn't change it, and a ``verdict'' quoted later doesn't
count. Any other line is read whole, in order: one that starts with ``incomplete'',
``inconclusive'' or ``not reviewed'', or says the diff, patch, files or code couldn't be read,
opened or found, is \code{incomplete}; then ``no changes'' or ``no blockers'' is \code{yes}; then
\code{CHANGES}, ``changes needed'' and the like are \code{changes}; then ``no-go'', ``not
approved'', ``not ok'', ``blocked'', ``reject'' or a leading ``no'' are \code{no}; then ``go'',
``ready'', ``approved'', ``LGTM'', a leading ``yes'' or a line that is just ``OK'' are \code{yes}.
Anything else has no verdict.

\code{server.py top} draws a status screen from that log and from files already on the computer,
with ANSI colours and the terminal's alternate screen: a top bar with each subscription's most
pressing window (the highest of used up, running out first, on pace past 90\%, then the most
used), with the word \code{busy} when that quota's week is on pace past 70\% (dropped first when the
bar is too narrow), boxed panels, and a bar of keys on the bottom line, which is written without a newline so
the screen never scrolls; lines stop one column short of the edge, for consoles that wrap at the
last one. Widths are counted in terminal cells (\code{unicodedata}: wide characters take two,
combining marks none). Below 149 columns the panels stack, at most 104 wide; from 149, the
subscriptions are cards 50 wide on the left. Colours are the 16 standard ones, with bright black
for the faint parts; a Windows console that isn't Windows Terminal, ConEmu or one that sets
\code{TERM} or \code{TERM\_PROGRAM} gets square corners and \code{|} for the bar's mark of time gone.
\code{read\_key} returns early when the terminal is resized or \code{OpenStatusScreen} sends a command, and reads an arrow or function key
whole (on Windows the two characters after \code{\textbackslash x00} or \code{\textbackslash xe0}, elsewhere an
escape sequence) so it does nothing. \code{?} shows a help page; Esc goes back from it and quits
otherwise. It redraws every 5 seconds, reads Codex's
usage from the daemon every 60 and the transcripts again every 300 in one background thread, and
Antigravity's quota every 60 in another, since \code{agy -p /usage} can take a minute; until its
first reading the Antigravity line says it is checking, and \code{r} only wakes both threads and
the consultations page's (below). The
log is read with the files it was rotated into. A period's replies are those to the messages
sent in it, each turn as it was first read; replies to earlier messages are counted apart.
Verdicts, reply times and review loops come from those replies, and a loop counts each turn once,
however many messages steered it. A saved Codex or Claude Code reading gives its pace as of when
it was saved, and none once it is over 30 minutes old. On a screen too short for it all, the
layout is tried at levels until one fits: the ``which kind went where'' and ``reasons given''
lists and the offload notes go first, then weeks down to three, then the consultations' tables,
then all but their first line and weeks down to one, then the consultations and the
subscriptions panels; each box closes, and the latest week stays in view. Below that, the
screen is cut, keeping the key bar.

The screen keeps to the \code{server.py} on disk. Before each redraw it compares the file's
modification time and size with those of the version it runs; once they have changed and stayed
the same for one redraw, and the new file compiles and still holds \code{def run\_top(} and the
\code{\_\_main\_\_} entry point (an empty file, or one cut short after a whole function, compiles too),
the screen starts again on it with the same period and page. The version it runs is passed to it as
\code{-{}-since <mtime>:<size>}, as the process starting it saw the file just before; only the first
screen started by hand takes it as Python loaded the file. A change after that, even while the
screen starts, restarts it. On every system \code{server.py top} runs the screen
as a child (\code{top -{}-screen}), noting the version just before, and reads its exit code: 70
when the user quit, 71 to start again as it was started, and 72 to 81 to start again with a page and
a period: \code{reload\_code} gives 72, plus 5 times the page's place in \code{TOP\_PAGES} (\code{usage},
\code{consultations}), plus the period's place in \code{TOP\_PERIODS} (1, 7 or 30 days, or all), or 4
to keep the period it was given. The supervisor rebuilds \code{-{}-days} and \code{-{}-page} from it. It starts the screen with \code{-{}-supervised}, so the screen knows the supervisor holds the single-screen lock (below) and takes these codes. A screen without it, restarted on this version by a 0.22.0 supervisor that knows only 71 to 75, holds the lock itself and asks for the usage page (71, or 72 to 76), since that supervisor would take 77 and above as a failure; if another screen holds the lock, it switches that one to its page and exits with 70, which closes its window. Once the screen has restarted, any
other code, 0 included (a file cut short after the entry point can do nothing and exit cleanly),
leaves the window waiting; it starts the screen again once \code{server.py} differs from the
version that failed, and Ctrl+C closes it. Ctrl+C reaches the screen and the supervisor
together; the supervisor waits for the screen to end and then exits, whatever code it ended with,
and ends a screen that hasn't within 2 seconds. Elsewhere than Windows, a \code{SIGTERM} or
\code{SIGHUP} to the supervisor ends the screen first: the signal only raises an exception, so the
screen is ended and reaped outside the interrupted wait, and one that comes while the screen is
starting is acted on once it has started. The screen takes \code{SIGTERM} as Ctrl+C, so it puts the
terminal back before it ends. The compile-and-markers check doesn't prove a file whole: one cut short after the entry
point passes, and its screen ends at once, which leaves the window waiting. The terminal goes into cbreak
mode inside the block that restores it, so an interrupt at any point leaves it as it was.

\subsubsection*{The consultations page}
\label{sec:consultations-page}

\code{c} switches the screen to its consultations page and back. nouez opens no window for a
consultant (up to 0.22.0 it opened a Codex pane, Section~\ref{sec:old-panes}); this page shows all of
them in one place instead. A \code{ConsultationFeed} reads its data in a thread of its own, so the
screen keeps answering keys: \code{load\_consultants} over one \code{CodexClient} kept open while the
screen runs, the unloaded ones found in Codex's index as Section~\ref{sec:resolve} describes (on
the usage page, which counts only busy consultants, the loaded ones alone), and the Antigravity
records in nouez's cache folder, every \code{TOP\_LIST\_SECONDS}
(12); and, only while the page is shown, the selected consultant's latest turn
(\code{thread/turns/list} with \code{limit} 1, or the last \code{agy/<id>/turns/} entry), every
\code{TOP\_TURN\_SECONDS} (1.5) while it runs. A turn that has ended is read once more and then not
again until the consultant's update time changes. A failed read drops the connection, which the next
read opens again. The feed knows a connection's \code{codex app-server proxy} from the moment it
starts (\code{on\_spawn}), so closing the screen ends it even while its handshake waits; a failed list keeps the Codex rows it had, with the error under them. The feed asks only
\code{thread/loaded/list}, \code{thread/read}, \code{thread/list} and \code{thread/turns/list}: it
sends no consultant anything.

The list (\code{consultant\_overview}) holds only nouez's own consultants (\code{is\_bridge}; a
session the user opened isn't listed), working ones first, then the most recently active, each
with its state, how long ago it was active, the verdict of the reply to its last message and that
message's \code{kind}, both from the usage log, and its project and model. The verdict shows only
when the logged reply belongs to the last logged send and the consultant isn't working. Below it, the
selected turn's items in order: the message (with the sender from the bridge header and the revision
line taken off, and the user's own words, when Claude Code passed them on, under a label of their own before it), thinking summaries, the commands it ran (with the exit code when one failed), searches
and the consultant's messages, the final reply in bold; then \emph{working…} or the error. Every
text from a consultant or the usage log (the turn's labels and sender, errors, a turn's state, a
message's kind and verdict, a model's name) goes through \code{page\_text} or \code{\_printable}, which turns tabs into spaces and drops
every character Python doesn't count as printable (controls, format characters such as
bidirectional overrides, separators other than the space), so a reply can't move the
cursor, change colours or reorder the line. The turn follows its end as it grows; Page Up, Page
Down and Home scroll back, End follows again. On a short screen the list gives up rows first, so
the turn keeps at least one line. Under the turn is the command that opens the consultant in its
own CLI, with its folder, cut from the left when it doesn't fit, since its end names the project.
\code{resume\_command} builds it in the feed's thread: for Codex, \code{codex resume <id> -{}-remote
unix://<socket>}, the control socket under the daemon's \code{codexHome} (from its \code{initialize}
answer), so a terminal with another \code{CODEX\_HOME} finds the thread too, and without
\code{-{}-remote} when that socket isn't there; for Antigravity, \code{agy -{}-conversation <id>}. Each
word after the program is quoted for the shell the user types it in, PowerShell on Windows and
bash or zsh elsewhere (\code{shell\_word}); \code{agy}'s full path is shown as
\code{agy\_shown} gives it, already in that form. The turn's
lines are laid out again only when the turn read or the width changes, and wrapped in one pass
(\code{wrap\_cells}), so a long reply doesn't slow every redraw.

\subsubsection*{One status screen}

The supervisor holds \code{status-screen.lock} in nouez's cache folder, taken without waiting, for as
long as it runs, across the screen's restarts, and writes its process id and an id of its own
(\code{uuid4}) to \code{status-screen.json}; it takes the lock, and writes that file, under
\code{status-command.lock}, as it removes the file and gives up the lock when it ends. If the file
can't be written, it gives the lock up again and runs the screen without it, since a request would
otherwise go to an id an earlier screen left there. It hands the id to the screen it starts in
\code{NOUEZ\_STATUS\_SCREEN}, and the screen trusts the file's \code{applied} only under that
id. A try that
fails while no screen holds the lock (the screen closed meanwhile) is tried again; only a cache folder that can hold no
lock runs the screen without it. A second \code{server.py top} that finds the lock held doesn't start
another screen: it writes a command for its \code{-{}-page} and \code{-{}-days}, if given, asks for the
open screen's window to be brought forward, says so and exits; if that screen closed meanwhile, it
tries again to run its own. \code{OpenStatusScreen}, under \code{status-open.lock} so two
sessions can't both open one, writes a command when a screen holds that lock:
\code{status-command.json} (\code{screen}, \code{seq}, \code{page}, and \code{days} when given),
and, on Windows, restores the screen's window from its entry in nouez's window records and asks for
it to be brought forward. \code{write\_status\_command} holds \code{status-command.lock} while it
checks the lock, reads the screen's id into \code{screen} and numbers the command after the one in
the file (\code{seq}, the time in nanoseconds when that is higher). So a command is addressed to the
screen registered when it was written, never to one that registers after it, and no two get the
same number. A command the screen hasn't applied yet is kept: a new one adds its fields to it, and a
bare \code{server.py top} writes none. A thread in the screen reads the file every half second and wakes \code{read\_key}; it
acts on a command addressed to it that isn't the last one it applied, which it records in
\code{status-screen.json} (\code{applied}): a command written while the screen restarts is applied
once it runs, and none twice. When no screen holds the lock, \code{OpenStatusScreen} opens a
window and waits up to 5 seconds for the new screen to take the lock, so a call right after it
switches that one rather than opening another; if the lock still isn't taken then, it says the
screen hadn't started yet rather than report it open.

When the Antigravity CLI is installed (\code{agy} on \code{PATH}, or on Windows
\code{\%LOCALAPPDATA\%\textbackslash agy\textbackslash bin\textbackslash agy.exe}), the screen also
runs \code{agy -p /usage -{}-output-format json} once a minute, with the deny rules of
section~\ref{sec:agy}. \code{/usage} is a read-only command: it
answers with \code{num\_turns} 0 and no tokens. nouez reads \code{command.data.groups}, each a
\code{name} and \code{buckets} with \code{window} (\code{weekly} or \code{5h}),
\code{remaining\_fraction} and \code{reset\_time}, and shows the percentage used,
$100 \times (1 - \textit{remaining\_fraction})$, like the other windows.

Token counts per week (weeks start on Monday, local time):

\begin{itemize}
\item \textbf{Claude Code:} \code{\textasciitilde/.claude/projects/**/*.jsonl}, the
  \code{message.usage.output\_tokens} of each \code{assistant} line, counted once per
  \code{message.id} (Claude Code writes one message over several lines). Files under a
  \code{subagents} folder count as subagents. A reply is also counted once across a session's
  transcripts: its own (\code{<project>/<id>.jsonl}) and its subagents'
  (\code{<project>/<id>/subagents/*.jsonl}). A forked subagent's transcript starts with a copy of
  its parent's history, with the same message ids, so a reply already counted in another transcript
  of the session isn't counted again: a reply counts in the first of the session's transcripts, in
  path order, that has it. Path order puts a session's own transcript before its subagents', so the
  copy is the one left out.
\item \textbf{Codex:} \code{rollout-*.jsonl} under \code{\textasciitilde/.codex/sessions} and
  \code{archived\_sessions}. \code{token\_count} events carry running totals
  (\code{info.total\_token\_usage}); nouez counts the growth since the last one. A forked session's
  totals start from zero, so a fork counts only its own turns. A file whose
  \code{session\_meta} has \code{thread\_source: "nouez"} is a consultant's. The latest
  \code{rate\_limits} seen stand in for the daemon when it can't be reached.
\end{itemize}

Only files changed in the last 13 weeks are read. For each, \code{usage-weeks.json} keeps the byte
offset read to (only whole lines count), its counts per week and, for a Claude Code transcript,
the message id of each reply it counted, so a later scan reads only what was added. A Codex file
that got shorter is read again from the start; a file that's gone drops out. A Claude Code session
is read again from the start, all its transcripts, when reading on could count differently from a
fresh scan: one of its transcripts got shorter, is gone or aged out (its replies may now count in
another), or a reply turns up in a transcript that comes before the one that counted it. So the
counts are always those of a fresh scan. A session with a transcript that can't be read keeps the
counts of the last scan until a later one can read it. A cache written by an older version is dropped and the
transcripts are read again.

\subsection{Antigravity consultants}
\label{sec:agy}

With \code{provider: "antigravity"}, \code{StartConsultant} makes a consultant on Google's
Antigravity CLI instead of the Codex daemon. Without \code{provider} it uses Codex when the codex
CLI is installed and Antigravity otherwise, and says so in its result; with neither it fails with
a message naming both CLIs and \code{server.py doctor}. \code{agy} is looked up on PATH, then, on
Windows, in its installer's folder \code{\%LOCALAPPDATA\%\textbackslash agy\textbackslash bin}. There is no daemon: each message runs one
\code{agy -p} process in the background, and nouez keeps the state in files under
\code{agy/} in its cache folder. \code{agy/}\textit{id}\code{/consultant.json} holds the name,
folder, model, title and standing instructions. \code{turns/}\textit{turn}\code{.json} holds a
turn's process id, start time and program, its model, and where in \code{.in} the message as
shown in history starts, beside its \code{.in}, \code{.jsonl} and \code{.err} files. The id is a
UUID nouez makes; agy's own conversation id comes from the first turn's events, and a stop
saves it in \code{consultant.json}. Ninety days after a stop the turn files are deleted, at a
server's start, under the consultant's lock: the record is read again there, its conversation id
saved first, and it is marked done only once every file went, so a file that couldn't be deleted
is tried at the next start. The record stays. Folders and turn files are made
without following links (\code{checked\_folder}, \code{new\_private\_file}), 0600 on macOS and Linux. Names are
\code{agy-}\textit{folder}\code{-}\textit{last 6 of the id}, with more of the id when another
consultant has that name, chosen under a lock for all Antigravity consultants; a name two
consultants share is refused. The other tools try these
names first and fall back to Codex.

\begin{wire}[nouez $\rightarrow$ agy: command line, then the one line on stdin]
agy --input-format stream-json --output-format stream-json --disable-slash-commands
    --model gemini-4-neon-high --print-timeout 30m --settings <deny rules>
    [--conversation <agy conversation id>] -p ""
{"event": "user", "message": {"content": "<preamble, instructions and message>"}}
\end{wire}

\begin{wire}[The deny rules: the value of the settings flag]
{"permissions": {"deny": ["write_file(*)", "command(*)", "mcp(*)", "execute_url(*)"]}}
\end{wire}

Probed against agy 1.5.14: \code{write\_file(*)} blocks every editing tool (\code{write\_to\_file},
\code{replace}, \code{multi\_replace}), inside and outside the folder; \code{command(*)} blocks
\code{run\_command}. Subagents and the browser tools aren't available in \code{-p} mode. The
\code{schedule} tool has no deny rule or setting; the first message's preamble asks the model not
to use it, \code{-{}-print-timeout} bounds a turn that waits on it, and the waiter says such a
turn may be stuck after \code{STALL\_SECONDS} without a new event.

Each output line is an event with \code{event} and \code{conversation\_id}, and an object named
after the event. nouez reads:

\begin{itemize}
\item \code{init}, for agy's conversation id;
\item \code{step\_update}: \code{text\_delta}, for the output so far;
\item \code{result}: \code{status}, \code{response}, \code{duration\_seconds} and
  \code{finished\_reason};
\item \code{result.usage}: \code{input\_tokens}, \code{output\_tokens}, \code{thinking\_tokens},
  \code{cache\_read\_tokens} and \code{total\_tokens}.
\end{itemize}

A turn is
\code{completed} on a \code{SUCCESS} result, \code{interrupted} when \code{finished\_reason} is
\code{print\_timeout} or nouez stopped it, and \code{failed} on another status or when the process
ended without a result (with the last lines of \code{.err}). Without a result, it is
\code{inProgress} while its process runs, checked by process id, start time and program, or for
30\,s after the turn started while the process can't be seen yet. nouez checks the process before
reading \code{.jsonl}: had agy already ended, the output read is complete, so a result written just
before agy exits is never taken for a failure. A turn whose process couldn't start is
\code{failed}, with the reason.

A message sent while a turn runs is refused, since agy can't steer one. A send and a stop take
one lock per consultant, a locked byte in its folder's \code{lock} file, shared by every nouez
server on the computer and freed by the system if a server dies; a send reads the consultant again
under it, so a stop or a model change from another session is seen. The first message carries
a read-only preamble and the standing instructions; later ones pass \code{-{}-conversation}. A
\code{model} or \code{effort} on \code{SendConsultantMessage} picks the id from
\code{agy models} (cached an hour): the family with the level appended, such as
\code{gemini-4-neon-low}; the id is checked again just before each turn starts.
\code{StopConsultant} opens a handle to the turn's process only if its start time and program
match those recorded at launch, ends it and its children with \code{taskkill /F /T}, waits for it to
exit, and only then marks the turn and the consultant stopped; meanwhile the turn is marked
\code{stopping}, which reads as \code{interrupted} once the process has gone but never hides one
that runs on. A reader that finds agy gone reads the turn's marks again before naming it failed,
so a stop that lands between its reads still reads as a stop; a stop that can't end agy retries
taking its mark back. The files stay, and agy keeps the conversation. Whether the process has
ended is asked of Windows (\code{WaitForSingleObject} with no wait, on a handle with
\code{SYNCHRONIZE}), not read from its exit code, which a process can set to 259, the value of
\code{STILL\_ACTIVE}. Elsewhere than Windows, only the server that started a process signals it. A process
that can't be checked counts as running until agy's limit and is never ended, and a stop that can't
end a turn changes nothing and says so. A turn whose record can't be written is removed; a process
whose id can't be saved is ended with its children before nouez says to send again. Replies are logged with \code{provider: "antigravity"} and \code{tokens}, and each
send with Antigravity's quota groups under \code{usage.antigravity}. \code{top} adds their
\code{output\_tokens} per week in its Antigravity column, whatever model the consultant runs.

\subsubsection*{The sign-in warning}

Claude Code's sign-in on a computer ends after a set time that using it doesn't extend, and
Claude Code gives the end as a range of days. Remote Control sessions that outlive it disconnect
until the user signs in again, at the computer. nouez runs \code{claude auth status -{}-text}
(20-second limit, the same cleaned environment as the sessions it opens, in the home folder so no
project's settings shape a reading every server shares) and keeps only the line
starting \code{Sign-in}. Claude Code prints it as \code{Sign-in ends: between A and B (T)},
\code{Sign-in ends: any day now, by B (T)} or \code{Sign-in may have ended: between A and B (T)},
where \code{T} is the end, \code{B} its UTC date and \code{A} the UTC date three days before
(\code{LOGIN\_EARLY\_DAYS}). nouez takes \code{T} as the last moment and \code{T} less the days
from \code{A} to \code{B} as the earlier end; without \code{T}, the local midnights of \code{A} and of
the day after \code{B}. The other lines, which name the account, are dropped. It saves the line, when
it was read, the time of the credentials file and the sign-in's context (Claude Code's config folder
and the names, never the values, of sign-in variables such as \code{ANTHROPIC\_API\_KEY}) in
\code{nouez/claude-login.json}, shared by every nouez server; a server whose context differs ignores
it, and it never opens the credentials file itself. The line is read again when it is an hour old
(10 minutes within the last week), or when the credentials file's time changes (a new sign-in), in a
background thread, so a tool gets the saved line; a server starts a read when it starts. A run that
finds no line, or can't start \code{claude}, is saved as such and tried again after the same time; a
reading that can't be saved isn't repeated by that server for 10 minutes.

From 7 calendar days before the earlier end, on the computer's clock, the results of \code{OpenClaudeSession},
\code{ListClaudeSessions} and \code{ListProjects} end with a warning. \code{ConsultantBudget}
shows the line under Claude Code's usage, reading it first if the saved one is old (waiting up to
25~s, \code{LOGIN\_WAIT\_SECONDS}, for a reading another thread started), and the warning when
there is one; each request uses one reading. The status screen's top bar always shows the date and
days left (\code{sign-in Dec 5, 12d}), grey until the warning is on, then amber, red from the day before the earlier end, then
\code{sign-in ending} and, past the last moment, \code{sign-in ended}. \code{NOUEZ\_NO\_LOGIN\_CHECK=1} turns all of it off.
\begin{plain}[Result text: appended warning]
Claude Code's sign-in on this computer ends soon (Sign-in ends: between 2026-12-05 and 2026-12-08 (2026-12-08T20:59:30.320Z)): renew before Sat Dec 05 (in 3 days). Renewing needs the computer: `claude auth login` in a terminal there, or /login in a Claude Code session there. Remote Control sessions disconnect once it ends. Tell the user.
\end{plain}
Past the earlier date it says ``may already have ended'', and past the last moment ``has ended''.

\subsection{Closing the panes of earlier versions}
\label{sec:old-panes}

Up to 0.22.0 nouez opened a pane or window running \code{codex resume <id>} for each Codex
consultant. A server closes those once, when it starts (\code{start\_pane\_cleanup}, a background
thread, so \code{initialize} never waits on it). It closes only panes an earlier nouez opened, which
carry a token right after \code{codex resume <id>}: \code{-c nouez\_pane=<token>}, which Codex ignores
as an unknown key. The token is \code{p} and 32 hex digits of HMAC-SHA256 over the thread id, keyed
with 32 random bytes in nouez's cache folder (\code{pane-key}, shared by the user's nouez servers;
made under a lock file all servers take and read again under it, and written in full under a name
of its own before it is moved into place). A shell the user opened can't hold the token, whatever
they type, so a \code{codex resume} they started stays open. Panes from before 0.16.0 carry no token
and are left open too.

On Windows nouez runs no command for this. It lists processes with
\code{CreateToolhelp32Snapshot}, and reads the command line of each \code{cmd.exe} through
\code{NtQueryInformationProcess} (the information class is
\code{ProcessCommandLineInformation}), split into arguments as the C runtime does. A pane nouez opened
is a \code{cmd.exe} whose own \code{/k} command is \code{codex resume <id>} followed at once by the
token, with nothing else for \code{cmd} to run; one whose \code{codex} runs through npm's
\code{node}, or has already exited, still counts. Once its \code{codex} has exited, the pane is a
prompt where the user may have started a program of their own, so the window is ended only while
nothing runs in it but its console host (\code{conhost.exe} or \code{OpenConsole.exe}) and that
viewer: a \code{codex.exe} or \code{node.exe} whose own command line, read through its handle, is
the same \code{codex resume} with the same id and token (\code{is\_viewer}). If anything else runs
in it, a process in it can't be opened, or the second snapshot fails or names a process under the
window that wasn't checked (one started since the first), nothing is ended.

OpenProcess(each child, grandchild ...), kept only if it started after its parent
CreateToolhelp32Snapshot again: kept only if each still has the same parent
each one a console host or the viewer, or nothing is ended
TerminateProcess(those, deepest first)       (codex, or node and codex, inside the pane)
TerminateProcess(34288, exit code 0)         (a clean exit lets Windows Terminal close the pane)
WaitForSingleObject(34288, 3 s)
\end{plain}

Every process is checked and ended through a handle opened before the check, so a process id
that passes to another program meanwhile is never touched. A child whose parent id was reused
isn't taken for the pane's: it started before its parent. Nor is a process that took a child's id
after the first snapshot: an open handle keeps an id from being reused, so the second snapshot,
taken with all of them open, names each one's real parent.
On Linux, with \code{os.pidfd\_open} (Python 3.9 or later, Linux 5.3 or later), nouez runs no command
either: for each process in \code{/proc} it opens a pidfd first, then reads
\code{/proc/<pid>/cmdline}, the argument list split on NUL bytes, so no space or quote can blur it
(\code{pane\_argv}: a program whose name starts with \code{codex}, then \code{resume}, an id, \code{-c}
and this thread's token). A process id reused after the pidfd was opened can't receive the signal.
macOS has no pidfd and \code{ps} reads a process's arguments only after picking it by id, so a
process that took a pane's id between the check and the signal would be ended; nouez leaves the
panes open there.
\begin{plain}[Closing an old pane (Linux)]
pidfd_open(<pid>)
read /proc/<pid>/cmdline    (codex... resume <id> -c nouez_pane=<this thread's token>)
pidfd_send_signal(fd, SIGTERM)
close(fd)
\end{plain}

\subsection{Starting and ending Claude Code sessions}
\label{sec:claude-os}

\code{OpenClaudeSession} opens a new window: in Windows Terminal with the command below,
otherwise in a new console (Windows), Terminal (macOS) or the first terminal emulator of the
list in Section~\ref{sec:os}. On macOS and Linux a launcher that exits with an error within 1.5
seconds (an emulator without a display) is reported with what it said, and with the command to run
yourself.

\begin{plain}[The window's command]
wt -w new -d <cwd> --title "Claude: <name>"
  <python> -I <path>/server.py claude <temp>/nouez-claude-<random>.json
\end{plain}

That helper reads and deletes the file, then starts Claude Code in \code{cwd}:

\begin{plain}[What the helper runs]
claude --remote-control <name> --name <name> --model <model> --effort <effort>
  [--resume <session id> --fork-session] [-- <prompt>]
\end{plain}

Claude Code sets \code{CLAUDECODE}, \code{CLAUDE\_CODE\_CHILD\_SESSION},
\code{CLAUDE\_CODE\_SESSION\_ID} and similar variables for every command it runs, and a
\code{claude} that inherits \code{CLAUDE\_CODE\_CHILD\_SESSION} doesn't save its transcript. So the
helper starts \code{claude} without \code{CLAUDECODE}, \code{CLAUDE\_PID}, \code{CLAUDE\_EFFORT},
\code{AI\_AGENT} and the \code{CLAUDE\_CODE\_*} variables Claude Code sets for its commands
(\code{CHILD\_SESSION}, \code{SESSION\_ID}, \code{BRIDGE\_SESSION\_ID}, \code{MESSAGING\_SOCKET},
\code{MESSAGING\_TOKEN}, \code{ENTRYPOINT}, \code{EXECPATH}, \code{SESSION\_ATTENDED},
\code{SSE\_PORT}); the user's own, such as \code{CLAUDE\_CODE\_OAUTH\_TOKEN}, stay. It looks for
\code{claude} only in the absolute folders on \code{PATH}: Windows would look in the current
folder first, which is the project. The prompt follows \code{-{}-}, so it can't be read as an option.

\code{ListClaudeSessions} reads Claude Code's registry of running sessions,
\code{\textasciitilde/.claude/sessions/<pid>.json} (\code{\$CLAUDE\_CONFIG\_DIR/sessions} when that is set). Claude Code doesn't document it; nouez reads
\code{pid}, \code{sessionId}, \code{cwd}, \code{name}, \code{status}, \code{kind} (only
\code{interactive} entries count), \code{procStart} and \code{bridgeSessionId} (Remote Control),
and skips entries it can't parse. A file can outlive its process, and a pid can be reused, so on
Windows an entry counts only while its process runs and was created at the recorded
\code{procStart} (\code{GetProcessTimes}); an entry without a valid \code{procStart} doesn't count.
Elsewhere, an entry counts while the pid exists. A session whose parent process is the
\code{server.py claude} helper, created before it, was opened by \code{OpenClaudeSession}.

On Windows, \code{CloseClaudeSession} opens handles to the session's process and its helper and
checks their creation times again; while the handles are open, neither pid can pass to another
process. For a helper's session it leaves an empty file, \code{<temp>/nouez-closed-<pid>}, which
tells the helper the end was intended, so it exits with code 0 and Windows Terminal closes the
window. Then:

\begin{plain}[Closing a session (Windows)]
taskkill /PID 20964 /T /F    (claude and its children: shells, MCP servers)
wait up to 5 s for it to end, else TerminateProcess; an error if it is still running
wait up to 3 s for the helper to exit, else TerminateProcess(helper, exit code 0)
\end{plain}
\begin{plain}[Closing a session (macOS, Linux)]
kill -TERM 20964             (then wait up to 5 s for it to end; an error if it doesn't)
\end{plain}

nouez refuses to close any of its own ancestor processes, which include the Claude Code session
it serves (on macOS and Linux it walks them with \code{ps -o ppid=}). On macOS and Linux, just
before the signal, it also checks with \code{ps} that the pid is still Claude Code (its program is
\code{claude}, a version under \code{claude/versions/}, or Node running \code{claude-code}) and
that the process started no later than 5 seconds after the session's \code{startedAt} in the
registry, so a pid the system has given to another program is never signalled. When it can't tell,
it signals nothing and says so.

\subsubsection*{Trust}
\label{sec:trust}

Claude Code asks whether the user trusts a folder the first time it runs there, and records the
answer in its state file, \code{\textasciitilde/.claude.json} (in \code{\$CLAUDE\_CONFIG\_DIR} when
that is set), as \code{hasTrustDialogAccepted = true} in the folder's entry under \code{projects},
with forward slashes in the folder's name on Windows. Claude Code's
documentation gives the rule nouez follows: outside a git repository, trust on a folder covers the
folders inside it, except git repositories; in a repository, trust is recorded for the
repository's root, and for a linked worktree, its main checkout's root. nouez finds that from the
worktree's \code{.git} file (\code{gitdir:}) and the \code{commondir} file in that git folder: when
the common git folder is a folder's \code{.git} directory and that folder holds more than it, the
folder is taken as the main checkout. A separate git folder (\code{-{}-separate-git-dir}) records no
link back to its checkout, and can itself be named \code{.git}, so a common folder named otherwise,
or a \code{.git} alone in its folder, means the trust is unknown. A separate \code{.git} kept beside
other files would still be taken for a checkout, as \code{git worktree list} takes it too. A
submodule is its own repository. So a trusted \code{C:/Users/me/Projects} covers \code{Projects/notes} but not the repository \code{Projects/nouez}. A state file that is
missing or can't be parsed also means nouez doesn't know.

\code{NOUEZ\_NO\_TRUST\_WRITE=1} refuses \code{trust: true} for a folder not already trusted on its
own before anything is written, even the folder \code{create: true} would make.
With \code{trust: true} nouez sets that one value, for the folder above, and nothing else. It
refuses the home folder, a drive's root and Claude Code's own folder (where Claude Code doesn't keep
trust), and a key it can't place. It reads the file and parses it, adding a \code{projects} table if there is none; a file it
can't read or parse, whose \code{projects} isn't a table, or whose entry for the folder isn't one, is
left alone. It checks that the changed JSON reads back equal to what it means to write (a number
too big for a float, or text that can't be written as UTF-8, means it leaves the file alone), then copies the file as
read to a new dated backup in its own folder (\code{\%LOCALAPPDATA\%\textbackslash
nouez\textbackslash claude-json-backups} on Windows, \code{\$XDG\_STATE\_HOME} or
\code{\textasciitilde/.local/state} elsewhere; a relative one is ignored; created private, and
on macOS and Linux a folder that isn't private, or is a link, stops the change), reads the copy back, and keeps
the newest 20. Just before replacing the file it reads it again: if a session has written it in
the meantime, it starts over from that version (three tries). The new text goes to a temporary
file of its own beside the state file and is moved into place in one step; half a second later
nouez reads the trust back.

That narrows the risk but can't remove it. Every running Claude Code session rewrites the state
file, with the user's MCP servers and project settings in it, and nothing outside Claude Code can
lock it, so a session saving in the instant between nouez's last check and its replace could lose
that change, and a session that rewrites the file from what it read earlier could drop nouez's.
The read-back catches the second; the backups are there for the first.

\subsection{Arranging nouez's windows (Windows)}
\label{sec:arrange}

On Windows, nouez puts the Windows Terminal windows it opened in a grid that fills one screen, and
arranges them again as they open, close or are moved if automatic arranging is on. Those are the Claude Code sessions from
\code{OpenClaudeSession}. It never moves another window: not the status screen, which stays where
the user puts it, nor a terminal the user opened, nor one Claude Code runs in.
Everything below uses \code{ctypes} and the Win32 API; on macOS and Linux nothing is recorded or
moved.

\subsubsection*{Recording a window}

The helper in each window (\code{server.py claude}, \code{server.py top -{}-arranged}) finds the
window it is shown in (the status screen's is recorded only to be brought forward, never arranged): its own console window, from
\code{GetConsoleWindow}, is a hidden pseudo-console window owned by the Windows Terminal window
(\code{GW\_OWNER}, class \code{CASCADIA\_HOSTING\_WINDOW\_CLASS}). Windows Terminal may show the
window a moment after the tab starts, so a background thread looks for up to 3 seconds. In a
console that isn't Windows Terminal's, it records nothing. Otherwise it writes
\code{windows/s<session>/<pid>-<start>.json} in nouez's cache folder, where \code{<session>} is
the Windows session (\code{ProcessIdToSessionId}): window handles and the arranger belong to one
sign-in, so two sign-ins to the same account keep their windows apart. Registering is best-effort:
if it fails in any way, the window opens and isn't arranged.

\begin{wire}[A window's entry]
{"hwnd": 1442270, "console": 790916, "pid": 21544, "start": 134087365512345678,
 "kind": "claude", "slot": 1795990211.4, "box": [0, 0, 960, 1128], "left": false}
\end{wire}

\code{pid} and \code{start} (the process's start time) identify the helper; an entry whose
helper has ended, or whose pid now belongs to another process, is deleted when entries are read.
\code{slot} orders the grid (the time the window opened, swapped when the user swaps two windows),
\code{box} is where nouez last put the window and saw it stay, and \code{left} marks a window taken
to another screen. The helper deletes its entry when it ends, so the others close up; the
last one also deletes \code{screen.json}. Every read and delete of these files checks the folders
and the file itself again, so none is reached through a link (Section~\ref{sec:usage}).

\subsubsection*{The arranger}

Writing an entry wakes the arranger, \code{server.py arrange}, starting it if automatic arranging is on and none runs (its
mutex, below, tells whether one does: the wake event can outlive the arranger while another process
holds it open). It is a process of its own, outside the helper's job object when Windows allows, so it outlives the window
that started it. One runs per user session: it holds the named mutex
\code{Local\textbackslash{}nouez-arranger}, and others signal its auto-reset event
\code{Local\textbackslash{}nouez-arrange-wake}. It is per-monitor DPI aware (v2), so every position
it reads or sets is in the screen's real pixels.

It never polls. It sleeps in \code{MsgWaitForMultipleObjectsEx} on the wake event, one process
handle per helper (to see one end; at most 62, the wait's limit with the event) and its message
queue, which brings:

\begin{itemize}
  \item WinEvents, through \code{SetWinEventHook} out of context, from only the Windows Terminal
        processes that hold nouez's windows: move and size start and end, minimize start and end,
        destroy, show and hide, location change (maximizing, Snap), and cloak and uncloak
        (a switch of virtual desktop). Events for those processes' other
        windows, or for a control inside a window, are dropped at once.
  \item Broadcasts to a hidden top-level window of its own: \code{WM\_DISPLAYCHANGE},
        \code{WM\_SETTINGCHANGE} for the work area (the taskbar), and the session being unlocked.
\end{itemize}

Each wake restarts a 300 ms timer, so a burst of events makes one pass once they stop. While a
window is being dragged (between move-size start and end, or with the left mouse button down) it
waits again. A pass after a screen change, the work area changing or an unlock takes no move as
the user's: Windows moved the windows. With no window left, it waits 10 seconds for another and
ends; it ends at once when arranging is turned off. Once it has let its mutex go, it reads the
entries again and starts a successor if a window registered meanwhile; after a failure (its window,
event or wait), it starts none, and the next window to register starts one.

\subsubsection*{A pass}

A pass runs under \code{pass.lock} in that folder, so the arranger and \code{ArrangeWindows} never move
windows at the same time:

\begin{enumerate}
  \item Read the entries, oldest slot first. Leave out a window that is closed, minimized,
        maximized, hidden or cloaked (on another virtual desktop), one whose console's owner is no
        longer that window (its tab was dragged into another window), and a second entry for the
        same window; clear their boxes.
  \item Pick the screen: the one named in \code{screen.json} (its device name, such as
        \code{\textbackslash\textbackslash.\textbackslash{}DISPLAY1}, which stays with it when
        screens are rearranged) while it is connected, else the oldest window's, else the main
        screen, and save it. The grid stays on that screen.
  \item In the arranger's passes, a window the user moved is taken as a request. Taken to another
        screen (its middle measured on another connected screen), it is marked \code{left} and stays there until it is moved back by hand or
        \code{ArrangeWindows} brings it back. Moved off its box with its middle inside another
        window's box, the two swap slots. Anywhere else (a nudge, a resize), it goes back.
  \item Choose the grid (below) for the screen's work area. Check each window's console owner
        again, then ask Windows Terminal to place it in its box with \code{SetWindowPos} and the
        flags \code{SWP\_NOACTIVATE}, \code{SWP\_NOZORDER} and \code{SWP\_ASYNCWINDOWPOS}. The
        outer rectangle is sized so that the visible part fills the box: the invisible resize
        border, the difference from \code{DWMWA\_EXTENDED\_FRAME\_BOUNDS}, is left out. The request is posted, so a
        Windows Terminal that has stopped responding (\code{IsHungAppWindow}, or one that
        hangs later) never holds up the arranger; the move's own events bring the next pass. A
        window on another screen than its box is only moved there, so it rescales before a later
        pass measures its border and sizes it.
  \item Measure, and save the box only if the window holds it, within 12 pixels at 100\%
        scaling; only then does it count as arranged. A window that won't take its box (a minimum
        size, a terminal that doesn't respond, an elevated Windows Terminal, which a normal process
        can't move) is asked at most three times for the same box, then left as it is, its box
        cleared so it is never taken as moved by hand.
\end{enumerate}

The arranger arranges only two or more windows. \code{ArrangeWindows} runs
\code{server.py arrange -{}-once}, which arranges even one, takes no move as a request, and brings
back the windows that left; it passes again, 0.3 seconds apart and at most four times, until no
window needs moving, so its counts are of windows seen in their boxes.

\subsubsection*{The grid}

For $n$ windows in a work area $W \times H$, nouez tries each column count $c$ from 1 to $n$ with
$r = \lceil n / c \rceil$ rows, keeping those where no column is empty and every box is at least
$560 \times 320$ pixels at 100\% scaling (about 60 by 16 characters), and picks the one whose box
shape $\frac{W/c}{H/r}$ is closest to 1.6 (by the absolute value of its logarithm). Columns
that hold one window fewer come first, so the oldest windows get the taller boxes: three windows
on a wide screen make one tall box on the left and two stacked on the right. If not all fit, the
grid is made for as many as fit, and the newest are left where they are. Box edges are computed
with integer division from the area's edges, so neighbouring boxes share their edge and fill the
area exactly; a window counts as in its box within the 12-pixel tolerance, so real windows can
leave or overlap a few pixels.

\code{auto} lives in \code{arrange.json} in nouez's cache folder; automatic arranging is off unless the file contains
\code{auto: true}.

starts every session in its own folder. \code{server.py dispatcher} keeps one such server, named

install default on the phone makes it \code{phone}; \code{-{}-projects} or \code{-{}-no-projects} at

and lists the folders that look like they hold projects: \code{\textasciitilde/Projects}, and each
folder holding two or more trusted folders, a folder in a git repository counting as the repository,
those that could be projects folders, each once, with their counts; none is chosen. The dispatcher's
nouez records trust only for a folder inside one of them, checked for the folder and for the one trust is
kept for (a worktree's main checkout): spelled under it exactly as it is set, case included, with no

fall back to (\code{projects\_folder\_problem}). The home folder itself is the one exception, and only
when picked from the phone after nouez's warning; trust is then still never recorded for the home

\paragraph{Phone setup and the settings file.} The phone can't answer an MCP prompt: with Claude Code
2.1.332 an elicitation form from a server in a Remote Control session shows only in the computer's
terminal, while Claude Code's own permission prompt for a tool does reach the phone. So nothing on the
phone depends on elicitation. nouez's switches can be set in \code{settings.json} beside

under a lock and never through a link; one that can't be read keeps every protection on (a set variable still wins) and the
projects folders unknown until \code{server.py settings reset} moves it aside (after which they are unpicked, unless a sign-in
start installed before 0.29 names \code{-{}-projects} or \code{-{}-no-projects}, recorded when it next starts). Four switches are

\code{phone}, \code{OpenClaudeSession} records trust without the report and yes when every project
settings file of the trust key, checkout and folder is absent or holds only quiet settings (the

unreadable, with neither \code{no\_trust\_write} nor \code{ask\_trust} on. \code{RestoreClaudeConfig}
lists the trust marks and MCP servers present in nouez's copies of this profile's \code{\textasciitilde/.claude.json}
and gone from it now, each MCP server by the program it runs or the site it reaches (never its
arguments, the rest of its address or a value, where a credential can sit unmarked), and nothing while

approve a new command on the phone. \code{NouezStatus} sums up the sign-in, the subscriptions,
consultants waiting, sessions, the dispatcher, the version and these settings, each said unknown or
off rather than left out. In the dispatcher the sign-in warning rides on every nouez tool result
once a day per server, counted when the result is sent; \code{ConsultantBudget}'s own sign-in lines,
part of its report, show it whenever asked.

\paragraph{Commands.} \code{setup} makes the folder (its parent must exist, except
\code{\textasciitilde/.nouez}), checks the projects folders (\code{dispatcher\_roots\_problem}: each a
folder, fit to hold trust, none the same as or inside another; without \code{-{}-projects}, the folder
above the dispatcher's must exist, except \code{\textasciitilde/.nouez}, and when it can't hold trust none
is picked, for the phone setup to pick), writes
\code{CLAUDE.md} from \code{DISPATCHER\_CLAUDE\_MD} when there is none, or in place of one an
earlier nouez wrote (\code{DISPATCHER\_MD\_EARLIER}: the SHA-256 of each earlier text, the projects
folder 0.23 and 0.24 filled in put back first), after a checked copy
\code{CLAUDE.md.nouez-}\textit{date}\code{-}\textit{time}\code{.bak}; any other is kept, with a
note. It merges allow rules
\code{mcp\_\_consultants\_\_}\textit{tool} for each of \code{DISPATCHER\_TOOLS} into
\code{.claude/settings.json}. It reaches that file only through a \code{.claude} that is a
plain folder (\code{SettingsFolder}: opened with \code{O\_NOFOLLOW} and used through its descriptor
on macOS and Linux, checked by path on Windows), reads it first, and refuses a link, or a file that
isn't a JSON object whose \code{permissions.allow} is a list; before changing it, it copies it to
\code{settings.json.nouez-}\textit{date}\code{-}\textit{time}\code{.bak} and compares the copy, and
it replaces the file only if it still holds what was read. A save by another program between that
last check and the replacement would be lost; the copy holds what was read. On Windows the folders
are checked again before a temporary file is removed, and one left by a failed write is removed too.
It warns when neither \code{\textasciitilde/.claude.json} (for every project or for that folder)
nor the folder's \code{.mcp.json} registers nouez as \code{consultants}, the name the rules use. \code{install} checks that the folder has \code{CLAUDE.md}, that

\code{CLAUDE\_CONFIG\_DIR} that isn't an absolute path or projects folders \code{setup} would refuse.
Given no \code{-{}-projects}, it keeps those the running supervisor for that folder and profile
records as given (\code{kept\_projects}), and stops if what it finds there has changed once it holds the lock. It holds
\code{dispatcher-install.lock} while it works (\code{uninstall} too), so two don't mix, and goes
on only when \code{dispatcher\_installed} finds no sign-in start of that name, or nouez's own:
\code{yes}, or \code{off} when it is turned off; \code{other} and one it can't read stop it.
\code{other} is a description or label not nouez's, or a command other than the one
\code{dispatcher\_command} makes, as \code{dispatcher\_argv\_ours} checks it: a Python by its full

without waiting on a pipe, that begins with \code{NOUEZ\_HEAD}), \code{dispatcher run -{}-folder}
\textit{folder}, \code{-{}-projects} \textit{dir} pairs or one \code{-{}-no-projects}, an optional
\code{-{}-config-dir} \textit{dir}, \code{-{}-sign-in}, and nothing else; on Windows also a task with more than one action, or whose principal is neither this
user's SID nor name (\code{windows\_user\_ids}), and on macOS a plist with a \code{Program}
key. It registers the sign-in start, which runs
\code{[python, -I, server.py, dispatcher, run, -{}-folder, }\textit{folder}\code{, -{}-sign-in]}, with
\code{-{}-config-dir} before \code{-{}-sign-in} when

supervisor to stop, and starts the new one, checking within \code{DISPATCHER\_START\_WAIT} that it
runs with that folder, projects folders, profile and \code{-{}-sign-in}, all while it holds
\code{dispatcher-install.lock}:

Files are written through a temporary file beside them, never through a link, readable by the
user only. \code{uninstall} removes only a sign-in start that is nouez's. Neither command ends
a process by its id: each writes \code{dispatcher.stop}, which the supervisor
looks for every second, and waits up to \code{DISPATCHER\_STOP\_WAIT} for \code{dispatcher.lock}
to come free, writing it again if a supervisor starting meanwhile deleted it; the request is
removed either way. Only a regular file counts as a request: anything else of that name keeps a
supervisor from starting, makes \code{install} and \code{uninstall} stop with a message, and is
listed by \code{dispatcher\_cache\_problems} in \code{doctor} and \code{status}. The dispatcher's
files are in \code{dispatcher\_dir}: \code{nouez} in the local application data folder
\code{SHGetKnownFolderPath} gives on Windows, else \code{.cache/nouez} in the home folder the
user database gives, which must be private. No environment variable moves it, so the
supervisor started at sign-in and the commands run from any shell meet there, and there is no
other folder to fall back on. \code{status} prints \code{dispatcher\_summary}
and the end of \code{dispatcher.log}. \code{-{}-dry-run} prints what \code{setup}, \code{install}
and \code{uninstall} would do.

\paragraph{The supervisor.} \code{run} takes \code{dispatcher.lock}, waiting up to 2 seconds; a
second supervisor then exits. Before starting \code{claude} it waits while
\code{dispatcher-install.lock} is held (\code{dispatcher\_may\_start}): a stop request meanwhile
makes it exit. One started with \code{-{}-sign-in} then starts \code{claude} only when
\code{dispatcher\_installed} finds nouez's sign-in start running exactly the command for its own
folder and profile (\code{same\_command}, which ignores the Python); another answer makes it exit,
and one it can't read is asked again every 5 seconds, \code{DISPATCHER\_SIGN\_IN\_TRIES} times, before
it exits. So a start that came late can't outlive \code{uninstall}. One that took the lock first
for another folder or profile while \code{install} worked would make the new one exit and then
exit itself: \code{wait\_for\_supervisor} reports it as \code{other}, and
\code{start\_new\_supervisor} asks it to stop and starts the new one again; install fails if
it doesn't stop. A record that says \code{stopped}, or is one already asked to stop, doesn't
count: the next supervisor holds the lock a moment before it writes its own.
Once it has that lock, a request left from before is deleted. It finds \code{claude} on the PATH, then in \code{\textasciitilde/.local/bin}
(on macOS also \code{/opt/homebrew/bin} and \code{/usr/local/bin}), and starts it with the
environment \code{OpenClaudeSession} uses, without the variables that mark a child session,
with \code{claude}'s folder first on the PATH and \code{CLAUDE\_CONFIG\_DIR} from
\code{-{}-config-dir}, with no window, its output piped. On Windows the supervisor first puts
itself in a job object named \code{Local\textbackslash nouez-dispatcher-}\textit{pid}\code{-}\textit{random},
saved in \code{dispatcher.json}, that ends everything in it when its last handle closes, so a
killed supervisor takes its \code{claude} with it; a job of that name that exists already is never
joined, and a supervisor that can't make or join its job exits without starting \code{claude}. Each run gets a second job of its own, nested in the first: \code{claude} starts suspended
(\code{CREATE\_SUSPENDED}), goes into it, and only then runs, so nothing it starts escapes, and
closing it ends that run only. What nouez starts from inside the supervisor's job
(\code{in\_dispatcher\_job}: \code{IsProcessInJob} on the named job), the session windows, the
status screen, the window arranger and the Codex daemon, asks to leave it
(\code{CREATE\_BREAKAWAY\_FROM\_JOB}), so it outlives the run; anywhere else it stays in its
caller's job, except Antigravity's turns, which always ask. On macOS and Linux \code{claude}
gets its own session, and the supervisor signals its process group (\code{SIGTERM}, then
\code{SIGKILL}) until no member is left (\code{group\_members}: \code{/proc} on Linux, \code{ps}
elsewhere; a member that has ended doesn't count), even when \code{claude} itself exited first. It
sees that exit without collecting it: with \code{waitid} and \code{WNOWAIT}, counting only an exit
or a kill (\code{si\_code}), not a stop, or, where Python has no \code{waitid} (macOS before
3.13), with a kqueue \code{NOTE\_EXIT} event (\code{exited\_kqueue}); where those can't look,
from the process table (\code{is\_zombie}), never by collecting it. It collects \code{claude} only after the
last signal, so the group's id stays its own: the supervisor sets \code{SIGCHLD} back to its
default, since ignored it collects \code{claude} as it exits, and a \code{claude} something else
collected anyway (\code{ECHILD}) has its group left alone. A supervisor killed rather than
stopped can leave that group running. A reader thread reads what is there as it comes (\code{read1}),
decodes it incrementally, splits on carriage returns and line feeds, and also looks at a line not
yet ended, since \code{claude} redraws its status in place. It removes terminal codes, drops lines
seen among the last \code{DISPATCHER\_RECENT}, and writes the rest to \code{dispatcher-claude.log}.
Only \code{claude}'s status line counts (\code{STATUS\_LINE}: a few symbols, the state, a
\textperiodcentered{} and the start of the server's name): \code{Connected} or \code{Reconnected}
marks the link up; \code{Connecting}, \code{Reconnecting}, \code{Disconnected} or
\code{Not connected} marks it down; a line that only mentions the word changes nothing. Each run is numbered, and a
reader's change counts only for its own run. Each change is saved to
\code{dispatcher.json}: the supervisor's and \code{claude}'s process ids, the folder, the
\code{server.py} it runs, the phase, when it connected, and
the next start after an exit.

A \code{claude} not connected within \code{DISPATCHER\_CONNECT\_WITHIN} is ended: it is most
likely at a question no one can answer. After an exit the supervisor waits
\code{DISPATCHER\_FIRST\_WAIT}, doubling each time up to \code{DISPATCHER\_MAX\_WAIT}, and back
to the first wait after a run of \code{DISPATCHER\_STEADY}. A stop request ends the wait at once.
Remote Control writes no entry to \code{\textasciitilde/.claude/sessions} for the server itself,
so its output is the only sign of the link; the conversations it starts do get entries.

\paragraph{Status.} \code{dispatcher\_status} tries the lock for an instant (held means
running), then reads \code{dispatcher.json}. Logs are opened without following a link or waiting
on a pipe, and only a regular file is read or written; a log whose \code{.1} isn't a regular
file stops growing at its cap. \code{doctor} reports it, and the status screen's top bar shows
\code{\textbullet{} dispatcher}, green while connected, amber while not, red when the supervisor
ended without stopping (it crashed, was killed, or couldn't check its sign-in start: phase
\code{failed}), nothing when it stopped as asked or none was ever set up; it looks again at most every 5 seconds. Another
\code{claude} whose first argument that isn't an option is \code{remote-control}, other than the
supervisor's own, is noted by its process id and \code{-{}-name} only, since two servers named the
same appear twice in the app. Its arguments are read as the process got them
(\code{/proc/}\textit{pid}\code{/cmdline} on Linux, \code{KERN\_PROCARGS2} on macOS, the command
line on Windows), so one run with \code{-p} or \code{-{}-print} isn't taken for a server; on other
systems only \code{ps}'s joined line is there, and only the process id is given.
