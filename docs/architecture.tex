\begin{abstract}
\noindent nouez is an MCP server that lets Claude Code consult live Codex sessions, and open, list and
close Claude Code sessions on the same computer. This document
describes nouez 0.12.0: how the pieces fit together, and an example of every message nouez sends
or acts on at each boundary: the MCP traffic between Claude Code and nouez, the WebSocket
JSON-RPC traffic between nouez and the Codex app-server daemon, the commands nouez runs on
the operating system, and its one request to GitHub, which looks for a newer nouez release. The daemon also sends notifications and its own requests, which nouez
discards and this document leaves out. Message shapes are as captured in runs with Claude Code
2.1.295 and Codex app-server daemon 0.162.0; client behaviour described here (the discovery
probe, progress tokens, the 120-second move to the background) was observed in those runs and is
not something nouez controls. Ids are invented, long objects are trimmed to the fields nouez
reads, and quoted error texts marked as excerpts are shortened.
\end{abstract}

\section{Overview}

Two coding agents look at a problem differently. nouez gives each a fixed role:
\ccname{} is the main developer and owns the work; \cxname{} is a consultant that Claude asks
for second opinions. Consultants that nouez starts run in a read-only sandbox, and
\code{StartConsultant} only ever reuses those. Claude can also message a Codex session the user
opened, by name and with \code{allow\_user\_session: true}, when the user asks; such a session
keeps the user's own permissions. Everything
happens from the single Claude Code terminal.

A message makes three hops (Figure~\ref{fig:components}):

\begin{enumerate}
  \item \textbf{Claude Code $\leftrightarrow$ nouez.} Claude Code starts \code{server.py} as a child
        process and speaks MCP to it: JSON-RPC~2.0, one JSON object per line on stdin/stdout.
  \item \textbf{nouez $\leftrightarrow$ Codex daemon.} A tool call that needs the daemon starts
        \code{codex app-server proxy} (usually once per call; WatchConsultant may connect twice),
        which relays its stdio to the daemon's local control socket.
        Over that pipe nouez performs a WebSocket handshake and then exchanges JSON-RPC messages
        in WebSocket text frames.
  \item \textbf{nouez $\rightarrow$ operating system.} To show a consultant to the user, nouez opens a
        terminal pane running \code{codex resume <id>}, which attaches to the same daemon
        session. It also checks for such panes and, on StopConsultant, tries to close them.
        The Claude Code session tools work only at this level: they open terminal windows
        running \code{claude}, read the files Claude Code keeps about its running sessions, and
        end processes.
\end{enumerate}

Three more tools serve a different purpose: they manage Claude Code sessions on the same computer,
so that a session driven from the Claude app with Remote Control can start another one in a
different project (\code{OpenClaudeSession}), see which are running (\code{ListClaudeSessions})
and end a stuck one (\code{CloseClaudeSession}). They don't involve Codex or talk to Claude Code;
they work through the operating system and the files Claude Code keeps
(Sections~\ref{sec:claude-tools} and~\ref{sec:claude-os}).

\section{Inside the server}
\label{sec:inside}

\code{server.py} is a single file using only the Python standard library. One thread reads
stdin; every request runs on its own worker thread, because a tool call can block for minutes
while Codex works.

\begin{figure}[H]
\centering
\begin{tikzpicture}[font=\small\sffamily]
  \node[box, draw=nz, minimum width=3.0cm, minimum height=1.3cm] (loop) at (0,0) {\textbf{read loop} \code{main()}\\\footnotesize one line $\rightarrow$ \code{json.loads}};
  \node[box, draw=nz, minimum width=2.6cm, minimum height=1.3cm] (route) at (4.6,0) {\textbf{\code{route(msg)}}\\\footnotesize never waits on a tool};
  \node[box, draw=nz, minimum width=3.2cm, minimum height=1.3cm] (work) at (9.4,0) {\textbf{worker thread}\\\footnotesize one per request\\\footnotesize \code{handle} $\rightarrow$ \code{dispatch} $\rightarrow$ tool};
  \node[box, draw=cx, minimum width=2.6cm, minimum height=1.3cm] (cx) at (14.0,0) {\textbf{\code{CodexClient}}\\\footnotesize new per call,\\\footnotesize closed in \code{finally}};
  \node[box, draw=gray, align=left, font=\footnotesize\sffamily] (reg) at (4.6,-3.0) {\textbf{shared state}\\

\code{route()} sorts each parsed line:

\begin{itemize}
  \item Not an object, an \code{id} that isn't a string or number (booleans included), or a
        request with \code{"id": null}: answer \code{-32600 Invalid Request} right away, from the
        read loop's thread.
  \item No \code{method}: it is Claude Code's answer to a request nouez sent (\code{roots/list}); wake the waiting thread. Answers nobody is waiting for are dropped.
  \item \code{notifications/cancelled}: set the Event of the named request, if it is still running. Malformed params are ignored.
  \item Anything else: register a cancel Event for \code{tools/call} before starting its worker
        thread, so a cancel that arrives while the worker starts up is not lost. (A cancel that
        arrives before its request has nothing to cancel and is ignored.)
\end{itemize}

Any exception inside \code{route()} is logged and the loop continues, so no single line can stop
the server. Inside the worker, \code{handle()} makes sure every request with an id gets a
response unless it was cancelled: if \code{dispatch()} raises, it answers
\code{-32603 Internal error: <exception>}. An exception inside a tool is different: it becomes an
\code{isError} result reading \emph{``Unexpected error: <exception>''}.

\subsection{Startup}

Claude Code 2.1.295 first probes the 2026-07-28 protocol with \code{server/discover}. nouez is a
legacy-lifecycle server, so it answers \code{-32601}, and Claude Code falls back to the
\code{initialize} handshake with protocol 2025-11-25.

\subsection{Tool calls and results}

In the captured runs, every \code{tools/call} from Claude Code 2.1.295 carried a progress token in
\code{\_meta}. Claude Code moved any call that ran past 120 seconds to the background, where its
result arrives later as a task notification.

While SendConsultantMessage or GetConsultantReply waits for a running turn, nouez answers a
progress token with \code{notifications/progress}: at most one every 10 seconds, with
\code{progress} counting up from 1 and no \code{total}, since a turn's length isn't known. The
message names the turn, the time waited so far and the latest line of output. None is sent once
the call is cancelled, and none without a token. In the runs before 0.4.0, Claude Code did not
display progress notifications.

\begin{wire}[nouez $\rightarrow$ Claude Code: progress while waiting]
{"jsonrpc": "2.0", "method": "notifications/progress", "params": {"progressToken": 14, "progress": 3,
  "message": "codex-nouez-4d9f17 is working on turn 01a1f3c4-8b20-7d55-b1e3-6a9c0f2e7d31 (waited 21s): Reading server.py ..."}}
\end{wire}

\begin{wire}[Claude Code $\rightarrow$ nouez: request envelope]
{"jsonrpc": "2.0", "id": 14, "method": "tools/call", "params": {
  "name": "SendConsultantMessage",
  "arguments": {"to": "codex-nouez-4d9f17", "message": "Review this diff for bugs: ..."},
  "_meta": {"progressToken": 14}}}
\end{wire}

A tool returns text. Problems the model can act on (a bad argument, an unknown consultant, a
daemon that isn't running) come back as a normal result with \code{isError: true}, so the model
reads the message. Requests that are malformed in the ways listed in Section~\ref{sec:errors}
get a JSON-RPC error instead.

\begin{wire}[nouez $\rightarrow$ Claude Code: success]
{"jsonrpc": "2.0", "id": 14, "result": {"content": [{"type": "text",
  "text": "Reply from codex-nouez-4d9f17:\n\nTwo issues. 1) ..."}], "isError": false}}
\end{wire}
\begin{wire}[nouez $\rightarrow$ Claude Code: tool error]
{"jsonrpc": "2.0", "id": 15, "result": {"content": [{"type": "text",
  "text": "Codex app-server daemon is not reachable, and starting it did not help. Run `codex app-server daemon start` in a terminal to see why, or open a Codex session."}],
  "isError": true}}
\end{wire}

\subsection{Protocol errors}
\label{sec:errors}

Each of these except \code{-32603} is covered by \code{tests/test\_protocol.py}; the
\code{-32603} message is an example, since nothing in the tests makes \code{dispatch()} fail.

\subsection{Connecting}

A tool call that gets past argument checks opens a fresh \code{CodexClient} (WatchConsultant may
open a second one) and closes it in a \code{finally} block, killing the proxy's process tree. The
connection has four steps:

\begin{figure}[H]
\centering
\begin{tikzpicture}[x=1cm,y=0.72cm]
  \lifelines{0/nouez/nz, 6/proxy/cx, 12/daemon/cx}{8.0}
  \msg{1.2}{0}{6}{spawn: codex app-server proxy}

  \msg{3.0}{0}{6}{HTTP GET / Upgrade: websocket}
  \ret{3.8}{6}{0}{HTTP/1.1 101 Switching Protocols}
  \side{3.8}{6}{15 s deadline, read on a side thread}
  \msg{4.8}{0}{12}{initialize (clientInfo nouez 0.12.0)}
  \ret{5.6}{12}{0}{userAgent, codexHome}
  \msg{6.4}{0}{12}{initialized (notification)}
  \msg{7.4}{0}{12}{requests for this tool call ...}
\end{tikzpicture}
\caption{Opening a connection to the daemon. Bytes pass through the proxy unchanged.}
\end{figure}

\begin{plain}[nouez $\rightarrow$ proxy stdin: WebSocket upgrade]
GET / HTTP/1.1
Host: localhost
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: q3Xv0m5cJ0n9aB1kL2pR8w==

\end{plain}

HTTP/1.1 101 Switching Protocols
Upgrade: websocket

If the proxy closes its output before answering, no daemon is listening (it does not survive a
restart of the computer). nouez then runs \code{codex app-server daemon start} once, without
pipes and waiting at most 30 seconds for the command, and retries the connection every half
second for up to 20 seconds. On Windows, when \code{MSYSTEM} says nouez runs under Git Bash (the
waiter runs in Claude Code's Bash tool), the command gets the environment without \code{MSYSTEM},
\code{SHELL} and \code{EXEPATH}, and without the \code{PATH} folders that hold \code{msys-2.0.dll}.
The daemon and its updater inherit that environment, and the update script's bare \code{tar} would
otherwise find GNU tar, which reads \code{C:} as a remote host. Only if that fails does it report \emph{``Codex app-server daemon is
not reachable, and starting it did not help. Run `codex app-server daemon start` in a terminal to
see why, or open a Codex session.''} If the proxy
says nothing within 15 seconds, \emph{``Codex app-server proxy did not respond within 15s.''}; for
any status other than 101, \emph{``WebSocket upgrade refused: <first 200 bytes of the header>''}.

\subsection{Frames}

\begin{center}\small
\begin{tabular}{@{}l l l@{}}
\toprule
\textbf{Opcode} & \textbf{Meaning} & \textbf{nouez does} \\
\midrule
\code{0x1} text, \code{0x0} continuation & a JSON message, possibly split & reassemble until FIN, then parse \\
\code{0x9} ping & keep-alive from the daemon & answer with \code{0xA} pong, same payload \\
\code{0x8} close & daemon is closing & stop reading; pending requests fail \\
\bottomrule
\end{tabular}
\end{center}

Frames nouez sends are masked, as RFC 6455 requires of clients: text frames for its messages and
pong frames for the daemon's pings. A received message over 64~MiB ends the connection. A reader
thread puts parsed messages on a queue; \code{request()} sends one message and waits up to 15
seconds for the response with the same \code{id}. Everything else the daemon sends meanwhile,
notifications and the daemon's own requests alike, is discarded. A consultant never waits on
those requests, because it was started with \code{approvalPolicy: "never"}.

\subsection{Message format}

The daemon speaks JSON-RPC without the \code{"jsonrpc"} member. Ids are integers counting from 1
on each connection.

\begin{wire}[nouez $\rightarrow$ daemon]
{"id": 1, "method": "initialize", "params": {"clientInfo": {"name": "nouez", "version": "0.12.0"}}}
\end{wire}
\begin{wire}[daemon $\rightarrow$ nouez]
{"id": 1, "result": {
  "userAgent": "codex-tui/0.162.0 (Windows 10.0.26200; x86_64) WindowsTerminal (nouez; 0.12.0)",
  "codexHome": "C:\\Users\\you\\.codex",
  "platformFamily": "windows", "platformOs": "windows"}}
\end{wire}
\begin{wire}[nouez $\rightarrow$ daemon]
{"method": "initialized"}
\end{wire}
\begin{wire}[daemon $\rightarrow$ nouez: an error response]
{"id": 7, "error": {"code": -32600, "message": "thread 01a1f3c2-... is not materialized yet"}}
\end{wire}

nouez turns an error response into \emph{``\textless method\textgreater{} failed: \textless message\textgreater''}. A few
messages mean ``this session has no history yet'' and are treated as an empty turn list rather
than a failure: \code{not materialized}, \code{missing source rollout}, \code{no rollout found},
\code{is empty}, \code{list\_turns is not supported yet}.

\subsection{Data shapes}

\begin{wire}[A thread (session), fields nouez reads; the daemon sends about 30]
{"id": "01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17",
 "cwd": "C:\\Users\\you\\Projects\\nouez",
 "model": "gpt-5.6-sol", "modelProvider": "openai",
 "status": {"type": "idle"},             // "idle" | "active" (+ "activeFlags") | "notLoaded" | "systemError"
 "threadSource": "nouez",                // null for sessions the user opened
 "ephemeral": false, "parentThreadId": null,
 "name": "Diff review", "updatedAt": 1791547200}
\end{wire}

The consultant's name is derived, not stored: \code{codex-} + the last folder of \code{cwd} +
\code{-} + the last six characters of the id, lower-cased: \code{codex-nouez-4d9f17}.

\begin{wire}[A turn, fields nouez reads]
{"id": "01a1f3c4-8b20-7d55-b1e3-6a9c0f2e7d31",
 "status": "completed",                  // "inProgress" | "completed" | "interrupted" | "failed"
 "error": null,                          // may be {"message": "..."} when failed or interrupted
 "items": [
   {"type": "userMessage", "content": [{"type": "text",
     "text": "[Message from Claude Code via the consultants bridge]\n\nReview this diff ..."}]},
   {"type": "agentMessage", "phase": "commentary", "text": "Reading server.py ..."},
   {"type": "agentMessage", "phase": "final_answer", "text": "Two issues. 1) ..."}]}
\end{wire}

\code{phase} is \code{"commentary"} for progress messages, \code{"final\_answer"} for the answer,
or \code{null}. For a turn that has ended, the reply is the text of all \code{agentMessage} items
with \code{phase: "final\_answer"}, or, if there are none, of the last \code{agentMessage}. For a
turn still running, nouez shows the \emph{output so far} instead: every \code{agentMessage}
after the turn's latest \code{userMessage}, whatever its phase, keeping the last 4,000
characters. A steered message adds a \code{userMessage} to the running turn, so output written
before it arrived is not shown as if it answered it. This is the snapshot from the latest poll;
nouez polls instead of following streamed events, so it may lag the session by one poll.

\subsection{Finding a session}
\label{sec:resolve}

A \code{to} that is a full thread id is read directly with one \code{thread/read}, plus
\code{thread/loaded/list} to know whether it is loaded. Every other \code{to} first lists
sessions, then matches. Listing costs one request per session, because \code{thread/list} omits
\code{threadSource}:

\begin{wire}[1. Sessions loaded in the daemon (paged)]
-> {"id": 2, "method": "thread/loaded/list", "params": {}}
<- {"id": 2, "result": {"data": ["01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17", "01a1e8a0-..."], "nextCursor": null}}
\end{wire}
\begin{wire}[2. Read each loaded session]
-> {"id": 3, "method": "thread/read", "params": {"threadId": "01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17"}}
<- {"id": 3, "result": {"thread": {"id": "01a1f3c2-...", "cwd": "C:\\Users\\you\\Projects\\nouez", "threadSource": "nouez", "status": {"type": "idle"}, ...}}}
\end{wire}
\begin{wire}[3. One page of up to 50 saved sessions, to find consultants the daemon has unloaded]
-> {"id": 5, "method": "thread/list", "params": {"limit": 50}}
<- {"id": 5, "result": {"data": [{"id": "01a1d9b7-...", "status": {"type": "notLoaded"}, ...}, ...], "nextCursor": "..."}}
-> {"id": 6, "method": "thread/read", "params": {"threadId": "01a1d9b7-..."}}     // kept only if threadSource == "nouez"
\end{wire}

Only that one page is read, so a consultant unloaded and older than the 50 sessions it holds is
not listed. Then \code{to} is matched, case-insensitively: an exact name or id first; otherwise a
unique id prefix or suffix (except for \code{StopConsultant}, which accepts only exact matches);
otherwise a direct \code{thread/read} of \code{to} as a full id, which reaches older consultants.
A name keeps only the id's last six characters, so two sessions can share one; such a name is
refused, and the full id has to be used.

\begin{plain}[Matching failures (isError results)]
'codex-nouez-4d9f17' names more than one session. Use the full thread id: 01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17, 01a20b55-0c9e-7a13-b6f1-77e0aa4d9f17
'01a1' is ambiguous. Matches: codex-nouez-4d9f17, codex-nouez-77c2e0
No Codex session named 'codex-nouez-4d9f1'. Sessions: codex-nouez-4d9f17, codex-api-0b13aa
No Codex session named '4d9f17'. Use its exact name or full thread id. Sessions: codex-nouez-4d9f17
\end{plain}

terminal; no new one was opened.''} The \code{watch} value of the latest StartConsultant call
also decides whether later sends open a pane. The ``Ignored'' line appears only when

only when there are user sessions; it is added to the ``Started'' result too.

older than the latest Codex release. nouez takes the latest version from
\code{<codexHome>/version.json}, the cache Codex keeps for its own update check, so this check
makes no network request. The CLI version comes from \code{codex --version} and the daemon's from
\code{userAgent}. The notice names only the part that is behind and appears once per server
process. It doesn't appear when the cache is missing or the user dismissed that version in
Codex. nouez updates nothing itself; Claude runs the commands if the user asks:
\begin{plain}[Result text: update notice]

\end{plain}

A notice that a newer nouez is out comes before the Codex one. When Claude Code sends
\code{initialize}, nouez starts a background thread that looks up the latest release, so no tool
call waits for it. The thread first reads \code{nouez/latest-release.json} in the user's cache
folder (\code{\%LOCALAPPDATA\%} on Windows, \code{\$XDG\_CACHE\_HOME} or
\code{\textasciitilde/.cache} elsewhere). An answer less than a day old is used as it is, and so
is a failed attempt less than an hour old, which gives no notice. Otherwise nouez asks GitHub,
with no credentials and a 3-second timeout on each network step (not a deadline for the whole
request: name lookup and several slow reads can take longer), and saves the result, a failure
included, through a temporary file of its own (\code{mkstemp}) and \code{os.replace}, so servers
starting together don't write into one file. Servers that start at the same moment may each ask.
GitHub sees the request's IP address and time and the version in \code{User-Agent}; the request
goes through any proxy set in the environment. A cache file over 4~KB, or one whose fields aren't a
finite time and a version of at most six digits per part, is ignored. A thread that can't start, or
any error in the check or the notice, leaves the \code{initialize} answer and the consultation as
they are. Setting \code{NOUEZ\_NO\_UPDATE\_CHECK=1} turns the lookup off.
\begin{plain}[nouez to GitHub (HTTPS)]
GET https://api.github.com/repos/jibarix/nouez/releases/latest
Accept: application/vnd.github+json
User-Agent: nouez/0.12.0

200 {"tag_name": "v0.13.0", ...}             (drafts and pre-releases are never "latest")
\end{plain}
nouez keeps the version only if the tag reads \code{v}$n.n.n$; anything else, and any failure
(offline, a proxy, a rate limit), means no notice. The notice appears once per server process,
only for a version newer than the running one. The command it gives uses the folder
\code{server.py} runs from, in single quotes, which PowerShell and POSIX shells read literally,
so a folder name like \code{\$(...)} can't run anything. A folder whose name has a \code{'} or a
control character gets no command: Claude is told to ask the user to run the pull. If the folder
isn't a git checkout, the notice points to the release page instead. Either way, Claude asks the
user to reconnect only after the update worked:
\begin{plain}[Result text: nouez update notice]
nouez 0.13.0 is out; this server is 0.12.0. What changed: https://github.com/jibarix/nouez/releases/tag/v0.13.0. Tell the user and go ahead with the consultation. Only if the user asks you to update, run `git -C 'C:/Users/you/nouez' pull --ff-only` in a shell. If git fails (local changes, a conflict, no branch checked out), stop there: tell the user what git said, don't ask them to reconnect, and don't discard, stash or switch anything without the user's say. Only after the pull succeeds, ask the user to run /mcp and reconnect consultants, which loads the new version; the Codex consultants keep their sessions.
\end{plain}

\subsection{SendConsultantMessage}
\label{sec:send}

The central tool. A lock per session, held only inside this nouez process, makes sure two of its
concurrent sends can't both start a turn; it does not cover other clients of the daemon, such as
the user typing in a Codex terminal. The lock is held through delivery, the check that the new
turn is listed, and opening the pane, and is released before the long wait, so a slow reply
doesn't block other senders.

\subsection{GetConsultantReply}

Reads a reply without sending anything. A send returns after 5 seconds by default, usually before
the reply is ready, and Claude is told not to wait for it but to run the waiter (next section) in
the background. Without background commands, it calls this tool with the returned
\code{turn\_id} when the user asks or when it next needs the reply, and the call returns at once.
When the user does want Claude to wait, it passes \code{wait: "done"}. That call returns when the turn ends, when an error occurs (such as a
lost daemon connection), or after the 4-hour cap, so a client that moved it to the background is
notified when the reply is ready, up to one 1.5-second poll late. An error or the cap is not a
reply; call again.

\subsection{The waiter command}

\code{server.py wait <thread\_id> <turn\_id>} is not a tool but a command line. A send that
returns before the reply, and a \code{GetConsultantReply} that finds the turn still working, give
it with full paths (\code{sys.executable -I} and the absolute path of \code{server.py}) and tell
Claude to run it as a background command. In Claude Code that is the Bash or PowerShell tool with
\code{run\_in\_background}: Claude is free at once, and when the command exits Claude Code wakes it
with the command's output, so the reply arrives without the user asking for it. A path is quoted
only if it contains a space (the command then adds that PowerShell needs \code{\&} before it), so
the command runs as is in either shell and a permission rule can match it by prefix.

\code{server.py allow-rule} prints those rules for the interpreter that runs it, one per shell tool:
\begin{plain}
Add these to permissions.allow in ~/.claude/settings.json:
"Bash(C:/Python313/python.exe -I C:/Users/you/nouez/server.py wait *)",
"PowerShell(C:/Python313/python.exe -I C:/Users/you/nouez/server.py wait *)"
\end{plain}
They name one interpreter and one script, so Claude Code keeps them in auto mode, which drops only
broad interpreter rules; without them it asks before each waiter, or auto mode may block it.

The waiter opens its own connection, resolves the thread by exact id, and looks for the turn among
its \code{REPLY\_LOOKBACK} (100) most recent turns. A turn that is missing ends it with exit
code~1. A turn that has already ended is printed at once; a running one, which is always among the
newest, is polled with \code{wait\_for\_turn} for up to \code{WAITER\_SECONDS} (25 minutes).
Claude Code stops a background command after 30 minutes by default, so at that point the waiter
exits with code~0 and the \emph{still working} result, including the output so far and the same
command to run again; Claude starts a new waiter. When the turn ends, the waiter prints
\emph{``The consultant's turn has ended (thread \ldots, turn \ldots).''} and the turn formatted as
\code{GetConsultantReply} would, with the reply cut at \code{WAITER\_REPLY\_CHARS} (20,000)
characters and the rest saved to a file, and exits with code~0. Its standard output is UTF-8.

A failed connection (\code{BridgeError}, or an \code{OSError} such as a broken pipe) is retried
10 seconds later, never past the 25-minute deadline. After \code{WAITER\_RETRIES} (3) failures in a
row, a count that each working connection resets, it prints \emph{``Stopped waiting for turn
\ldots''} with a pointer to \code{GetConsultantReply} and exits with code~1. The waiter dies with
the Claude Code session that started it; the reply stays readable with \code{GetConsultantReply}.

\subsection{Claude Code sessions}
\label{sec:claude-tools}

\code{OpenClaudeSession} takes \code{cwd} (required, an absolute path), \code{name} (default: the
folder's name; letters, digits, spaces, \code{.}, \code{\_} and \code{-}, starting with a letter or
digit, up to 64 characters, so it can't be read as an option), an optional first \code{prompt}, \code{model} (default \code{opus}, the latest
Opus), \code{effort} (default \code{medium}), \code{create}, \code{trust} and
\code{open\_untrusted}. The session starts with \code{--model} and \code{--effort} from those, not
the user's own Claude Code defaults, and with \code{CLAUDE\_CODE\_EFFORT\_LEVEL} set to the same
effort, since that variable outranks the flag; a model must be an alias or a full model name, so it can't read
as another option. With
\code{create: true} a missing folder is made (its parent must exist). It writes \code{cwd}, name, prompt,
model and effort to a temporary file and opens a new terminal window running \code{server.py claude <file>}
(Section~\ref{sec:claude-os}); the window reads the file, deletes it, and starts Claude Code.

First it checks whether Claude Code has been trusted in the folder (Section~\ref{sec:trust}),
since a session waiting at the trust question can't connect. If not, nothing opens and the result
tells Claude to ask the user whether they trust the folder. Only if they say yes does Claude call
again with \code{trust: true}: nouez records the answer as the trust dialog would, after backing up
Claude Code's state file (Section~\ref{sec:trust}), and opens the window, so it works from the
phone. \code{open\_untrusted: true} opens the window untrusted instead, with a warning, for a user
at the computer who would rather answer Claude Code's own question. If nouez can't tell, the window
opens and the result says the session may be waiting at the question.

\begin{wire}[Claude Code $\rightarrow$ nouez]
{"jsonrpc": "2.0", "id": 19, "method": "tools/call", "params": {"name": "OpenClaudeSession", "arguments": {"cwd": "C:\\Users\\me\\Projects\\other"}}}
\end{wire}

Checked: it is running and connected to Remote Control.
\end{plain}
Before opening, nouez reads the session registry (Section~\ref{sec:claude-tools}); after
opening a trusted folder, it reads it once a second for up to 15 seconds, looking for a new pid in
that folder, and ends the result with what it found. The window opens either way, and a registry it
can't read only leaves the note out. A session already running in the folder is named too.
\begin{plain}[Result text: other endings]

... Checked: it is running, but hadn't connected to Remote Control after 15s. It may still be connecting, or waiting for an answer on the computer.
... Checked: it hadn't shown up as a running session after 15s. It may still be starting, or waiting for an answer on the computer; ListClaudeSessions shows it once it runs.
\end{plain}

\subsection{Opening a pane}

The pane runs the daemon's own \code{codex} binary when nouez can find it, because a viewer whose
version differs from the daemon's can refuse to attach and offer to restart the shared daemon.
nouez reads the daemon's version from \code{userAgent} and looks under
\code{<codexHome>/packages/app-server-daemon/releases/<version>-*/bin/}, confirming with
\code{codex --version}.

\begin{center}\small
\begin{tabularx}{\textwidth}{@{}l >{\ttfamily\raggedright\arraybackslash}X@{}}
\toprule
\textbf{Where Claude Code runs} & \textrm{\textbf{Command nouez starts}} \\
\midrule
tmux (\code{\$TMUX} set) & tmux split-window -h -c <cwd> '<codex> resume <id>' \\
Windows Terminal (\code{\$WT\_SESSION}) & wt -w 0 split-pane -V -d <cwd> --title "Codex consultant" cmd /k <codex> resume <id>, with Claude Code's window brought to the front first (below); new-tab instead of split-pane when Claude Code's tab isn't selected; -w new when the window can't be found or brought to the front. In every argument after -w, \code{;} is passed as \code{\textbackslash;} (wt splits commands at a bare one) \\

Windows, no \code{wt} & cmd /c start "Codex consultant" cmd /k <codex> resume <id> \\

\subsubsection*{Finding Claude Code's window (Windows Terminal)}
\label{sec:wt-host}

\code{wt.exe} can name a window only by number or name, and \code{-w 0} means the most recently
used window, which may belong to another Claude Code session. So nouez first finds the window that
shows its own Claude Code session. Claude Code starts \code{server.py} without a console, so nouez
borrows one: walking up its parent processes, it calls \code{AttachConsole} on each until one has a
console, which is Claude Code's. In Windows Terminal that console's window
(\code{GetConsoleWindow}) is a hidden pseudo-console window, owned by the terminal window it is
shown in (\code{GetWindow(..., GW\_OWNER)}, class \code{CASCADIA\_HOSTING\_WINDOW\_CLASS}).
\code{AttachConsole} and \code{FreeConsole} replace the standard handles, which carry the MCP pipes
and are what \code{subprocess} hands to children, so nouez saves them first and restores them after
each attempt. The lookup runs under a lock, as a process has only one console at a time.

nouez then brings that window to the front (\code{AttachThreadInput} to the foreground thread,
\code{SetForegroundWindow}) and checks that it is in front. Attaching makes nouez wait on the
foreground program, so it skips that step when \code{IsHungAppWindow} says the program isn't
responding. It compares the console's title with
the window's, ignoring the spinner Claude Code animates at the start: the window shows the title of
its selected tab, so a mismatch means another tab is selected, and \code{split-pane} would split
that one. nouez runs \code{wt -w 0 split-pane ...} (or \code{new-tab ...}), waits for
\code{wt.exe} to exit and another half second for the terminal to act on it, and gives the
focus back to the window that had it. If the window can't be found or brought to the front, the
consultant gets a window of its own (\code{wt -w new}). Two gaps remain: another window that
comes to the front between the check and \code{wt} gets the pane, and two tabs with the same
title look alike.

\subsection{Detecting and closing panes}

Thread ids are checked against \code{[0-9A-Za-z-]+} before they appear in any command: opening a
pane refuses a malformed id with an error, and the checks and closing skip it.

\begin{plain}[Is a viewer already running? (Windows)]
powershell -NoProfile -NonInteractive -Command
  @(Get-CimInstance Win32_Process -Filter "Name='codex.exe'" |
    Where-Object { $_.CommandLine -like '* resume 01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17*' }).Count
-> 1
\end{plain}
\begin{plain}[Is a viewer already running? (macOS, Linux)]
pgrep -f "codex[^ ]* resume 01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17"
\end{plain}
\begin{plain}[Closing on StopConsultant (Windows), abridged: find the cmd windows nouez opened, with their children]
powershell ... Get-CimInstance Win32_Process -Filter "Name='cmd.exe'" |
  Where-Object { $_.CommandLine -like '*/k *codex* resume 01a1f3c2-...' } | ForEach-Object { "$p $k" }
-> 18244 20112
taskkill /PID 20112 /T /F            (codex inside the pane)
TerminateProcess(18244, exit code 0) (cmd; a clean exit lets Windows Terminal close the pane)
\end{plain}
\begin{plain}[Closing on StopConsultant (macOS, Linux)]
pkill -f "codex[^ ]* resume 01a1f3c2-5e7b-7c41-9a0d-2b6e8c4d9f17"
\end{plain}

The last two lines are what nouez does, not commands it runs: \code{taskkill} is run per child,
and the cmd process is ended through the Win32 \code{TerminateProcess} call.

Each check and close command has a timeout (20~s; 10~s for \code{codex --version}). When it
fires, nouez stops reading the command's pipes, because on Windows a grandchild process can keep
a pipe open forever, and kills the process: the whole tree on Windows (\code{taskkill /T}), only
the direct process elsewhere. A pane started with \code{tmux}, a new terminal window or \code{wt -w new}
is started without waiting, so it has no timeout. In Claude Code's own Windows Terminal window,
nouez waits for \code{wt.exe} to exit (up to 10~s) and then half a second more, besides finding
the window and bringing it to the front (Section~\ref{sec:wt-host}), so that call can take that long.

\subsection{Starting and ending Claude Code sessions}
\label{sec:claude-os}

\code{OpenClaudeSession} opens a new window: in Windows Terminal with the command below,
otherwise in a new console (Windows), Terminal (macOS) or the first of
\code{x-terminal-emulator}, \code{gnome-terminal} and \code{xterm} (Linux).

\begin{plain}[The window's command]
wt -w new -d <cwd> --title "Claude: <name>"
  <python> -I <path>/server.py claude <temp>/nouez-claude-<random>.json
\end{plain}

That helper reads and deletes the file, then starts Claude Code in \code{cwd}:

\begin{plain}[What the helper runs]
claude --remote-control <name> --name <name> --model <model> --effort <effort> [-- <prompt>]
\end{plain}

Claude Code sets \code{CLAUDECODE}, \code{CLAUDE\_CODE\_CHILD\_SESSION},
\code{CLAUDE\_CODE\_SESSION\_ID} and similar variables for every command it runs, and a
\code{claude} that inherits \code{CLAUDE\_CODE\_CHILD\_SESSION} doesn't save its transcript. So the
helper starts \code{claude} without \code{CLAUDECODE}, \code{CLAUDE\_PID}, \code{CLAUDE\_EFFORT},
\code{AI\_AGENT} and the \code{CLAUDE\_CODE\_*} variables Claude Code sets for its commands
(\code{CHILD\_SESSION}, \code{SESSION\_ID}, \code{BRIDGE\_SESSION\_ID}, \code{MESSAGING\_SOCKET},
\code{MESSAGING\_TOKEN}, \code{ENTRYPOINT}, \code{EXECPATH}, \code{SESSION\_ATTENDED},
\code{SSE\_PORT}); the user's own, such as \code{CLAUDE\_CODE\_OAUTH\_TOKEN}, stay. It looks for
\code{claude} only in the absolute folders on \code{PATH}: Windows would look in the current
folder first, which is the project. The prompt follows \code{--}, so it can't be read as an option.

\code{ListClaudeSessions} reads Claude Code's registry of running sessions,
\code{\textasciitilde/.claude/sessions/<pid>.json} (\code{\$CLAUDE\_CONFIG\_DIR/sessions} when that is set). Claude Code doesn't document it; nouez reads
\code{pid}, \code{sessionId}, \code{cwd}, \code{name}, \code{status}, \code{kind} (only
\code{interactive} entries count), \code{procStart} and \code{bridgeSessionId} (Remote Control),
and skips entries it can't parse. A file can outlive its process, and a pid can be reused, so on
Windows an entry counts only while its process runs and was created at the recorded
\code{procStart} (\code{GetProcessTimes}); an entry without a valid \code{procStart} doesn't count.
Elsewhere, an entry counts while the pid exists. A session whose parent process is the
\code{server.py claude} helper, created before it, was opened by \code{OpenClaudeSession}.

On Windows, \code{CloseClaudeSession} opens handles to the session's process and its helper and
checks their creation times again; while the handles are open, neither pid can pass to another
process. For a helper's session it leaves an empty file, \code{<temp>/nouez-closed-<pid>}, which
tells the helper the end was intended, so it exits with code 0 and Windows Terminal closes the
window. Then:

\begin{plain}[Closing a session (Windows)]
taskkill /PID 20964 /T /F    (claude and its children: shells, MCP servers)
wait up to 5 s for it to end, else TerminateProcess; an error if it is still running
wait up to 3 s for the helper to exit, else TerminateProcess(helper, exit code 0)
\end{plain}
\begin{plain}[Closing a session (macOS, Linux)]
kill -TERM 20964             (then wait up to 5 s for it to end; an error if it doesn't)
\end{plain}

On Windows, nouez refuses to close any of its own ancestor processes, which include the Claude
Code session it serves. Elsewhere it knows only its parent process (\code{os.getppid}), so a
wrapper between Claude Code and nouez would hide the caller from that check.

\subsubsection*{Trust}
\label{sec:trust}

Claude Code asks whether the user trusts a folder the first time it runs there, and records the
answer in its state file, \code{\textasciitilde/.claude.json} (in \code{\$CLAUDE\_CONFIG\_DIR} when
that is set), as \code{hasTrustDialogAccepted = true} in the folder's entry under \code{projects},
with forward slashes in the folder's name on Windows. Claude Code's
documentation gives the rule nouez follows: outside a git repository, trust on a folder covers the
folders inside it, except git repositories; in a repository, trust is recorded for the
repository's root, and for a linked worktree, its main checkout's root. nouez finds that from the
worktree's \code{.git} file (\code{gitdir:}) and the \code{commondir} file in that git folder: when
the common git folder is a folder's \code{.git} directory and that folder holds more than it, the
folder is taken as the main checkout. A separate git folder (\code{--separate-git-dir}) records no
link back to its checkout, and can itself be named \code{.git}, so a common folder named otherwise,
or a \code{.git} alone in its folder, means the trust is unknown. A separate \code{.git} kept beside
other files would still be taken for a checkout, as \code{git worktree list} takes it too. A
submodule is its own repository. So a trusted \code{C:/Users/me/Projects} covers \code{Projects/notes} but not the repository \code{Projects/nouez}. A state file that is
missing or can't be parsed also means nouez doesn't know.

With \code{trust: true} nouez sets that one value, for the folder above, and nothing else. It
refuses the home folder, a drive's root and Claude Code's own folder (where Claude Code doesn't keep
trust), and a key it can't place. It reads the file and parses it, adding a \code{projects} table if there is none; a file it
can't read or parse, whose \code{projects} isn't a table, or whose entry for the folder isn't one, is
left alone. It checks that the changed JSON reads back equal to what it means to write (a number
too big for a float, or text that can't be written as UTF-8, means it leaves the file alone), then copies the file as
read to a new dated backup in its own folder (\code{\%LOCALAPPDATA\%\textbackslash
nouez\textbackslash claude-json-backups} on Windows, \code{\$XDG\_STATE\_HOME} or
\code{\textasciitilde/.local/state} elsewhere; a relative one is ignored; created private), reads the copy back, and keeps
the newest 20. Just before replacing the file it reads it again: if a session has written it in
the meantime, it starts over from that version (three tries). The new text goes to a temporary
file of its own beside the state file and is moved into place in one step; half a second later
nouez reads the trust back.

That narrows the risk but can't remove it. Every running Claude Code session rewrites the state
file, with the user's MCP servers and project settings in it, and nothing outside Claude Code can
lock it, so a session saving in the instant between nouez's last check and its replace could lose
that change, and a session that rewrites the file from what it read earlier could drop nouez's.
The read-back catches the second; the backups are there for the first.
