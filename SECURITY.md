# Security

## Reporting a vulnerability

Please report it privately, through GitHub: [Report a vulnerability](https://github.com/jibarix/nouez/security/advisories/new) (the repository's **Security** tab → **Advisories** → **Report a vulnerability**). Don't open a public issue for it. Your report starts in triage, seen only by you and the people with access to the repository's security advisories. Once it is accepted it becomes a draft advisory, where the fix is worked out. The advisory is published with the release that fixes it, crediting you unless you'd rather not be named. Expect a first answer within a week.

Only the latest release gets fixes. nouez has no package: you run it from a clone, so an advisory reaches you through GitHub (watch the repository's releases, or its security advisories), not through Dependabot.

## What nouez does and doesn't do

nouez is one Python file, `server.py`, using only Python's standard library. It sends no telemetry: there is no nouez server, and nothing about you or your use of it is sent to its author.

`verify.py static` checks some of the lines below in `server.py`'s code on every run, in CI too (`boundary_problems` in `.claude/skills/verify/verify.py`):

- no network module is imported;
- web requests go only through `fetch_json`, to a URL built on `RELEASES_URL` or `AA_MODELS_URL`, which hold the two addresses below;
- a credential file is named only where its time is read, and not opened there;
- no word that bypasses permissions, and no `curl`, `wget` or `Invoke-WebRequest`;
- Codex consultants are read-only, with approvals `never`;
- Antigravity's deny rules are all there.

Those are regression checks that catch a plain change, not proof: an alias or a dynamic import gets past them. `fetch_json` itself also refuses to start at any other address.

### What leaves your computer

nouez itself makes two web requests, both through one function (`fetch_json`) that starts only at these two addresses and follows a redirect only on the same site (scheme, host and port):

| To | When | What it sends | Turn off |
|---|---|---|---|
| GitHub, `api.github.com/repos/jibarix/nouez/releases/latest` | In the background when a server starts, and in the phone dispatcher after one of its tools is used, at most hourly: an answer is reused for a day, a failed lookup waits an hour | An HTTPS request with `nouez/<version>` as the client name; GitHub sees your IP address | `NOUEZ_NO_UPDATE_CHECK=1` |
| Artificial Analysis, `artificialanalysis.ai/api/v2/language/models/free` | `ConsultantBudget`, only with a key set: about once a week, six hours after a failure, or with `refresh: true` once the scores are an hour old | Your key, the page number and the client name | Leave `ARTIFICIAL_ANALYSIS_API_KEY` unset, on Windows in your user environment variables too |

Everything else goes through the CLIs you installed, as they would if you ran them yourself. With a consultant CLI installed, Claude can send your diff or question to that provider without asking you each time, for example for a review before committing a behavior change. See [when Claude consults on its own](docs/rules.md#rule-automatic-consultation). Set `NOUEZ_NO_AUTO_CONSULT=1` in nouez's environment to turn that off.

- **Codex** (the app-server daemon): a consultant's messages, and the files and command output it reads, go to OpenAI. nouez asks the daemon for your usage:
  - once a minute while `server.py top` runs;
  - with each message the usage log records;
  - with each message that starts a new turn, before it goes, usage log or not;
  - in `ConsultantBudget`, which also lists the models.

  With Codex's default settings a consultant can also use OpenAI's hosted web search, in its `cached` mode: it reads pages from OpenAI's index rather than fetching them live, but its queries go to OpenAI's search and can hold text from a file it read, and a page it finds can carry instructions. nouez doesn't change that setting. To turn web search off for all your Codex use, consultants included, put `web_search = "disabled"` at the top level of `~/.codex/config.toml` (in `CODEX_HOME` if you set it).

  A consultant gets none of your Codex add-ons: nouez switches off, for its session only, every MCP server and plugin in Codex's settings for its folder (yours and the project's `.codex` ones) and the ChatGPT apps (connectors), when it starts and again before each new message. The read-only sandbox covers Codex's own tools, not these, and an MCP server can write wherever it is able to (a time tracker deleting entries, say). Codex sessions you opened yourself keep them. When Codex's settings can't be read, nouez starts and sends nothing.

  `doctor` runs `codex login status`. The status screen's consultations page reads each consultant’s latest turn and recent turns needed to verify continuations. It reads full details for the selection. The daemon answers locally.
- **Antigravity** (`agy`): a consultant's messages go to Google. It can search the web (Google's summary of the results, with their sources) but can't open a page: agy has no page-reading tool in a headless run, and nouez denies commands, so it can't fetch one either. nouez runs `agy -p /usage` for your quota, which asks Google without a model turn:
  - once a minute in `top`;
  - for each Antigravity message the usage log records;
  - for a message that starts a new turn on nouez's pick, usage log or not (a reading from the last 90 seconds is reused; for a model passed by hand, only in the background);
  - in `ConsultantBudget` and `doctor`.

  It runs `agy models`, kept an hour, in `ConsultantBudget`, `StartConsultant` and a send that changes the model or effort. **A review with `revision: true` sends the diff's text to Google in the message, by default** (deleted lines and untracked files included); `attach_diff: false` sends only the revision line.
- **Claude Code**: a session `OpenClaudeSession` starts runs with Remote Control, through Anthropic; its name defaults to the folder's name. nouez runs `claude auth status --text` for the sign-in line. It does so hourly, every 10 minutes while that line warns, and when the credentials file's time changes. `NOUEZ_NO_LOGIN_CHECK=1` turns it off.
- **Claude Code, the phone dispatcher**: after `server.py dispatcher install`, a supervisor starts at each sign-in and runs `claude remote-control --name dispatcher --spawn same-dir` in the dispatcher folder, through Anthropic, until you sign out or run `dispatcher uninstall`. It connects out; nothing listens on the computer. Anyone signed in to your claude.ai account can start a session there.
- **Claude, through nouez's tool results**: what a tool returns goes into the conversation of the Claude Code session that called it, and so to Anthropic. That includes consultant replies, history, folder reports and errors. A folder report lists the project's hooks, MCP servers and permission rules. nouez masks what looks like a secret in them (key-like values, `token=`, `Authorization:` and similar headers). Masking can't recognise every secret, such as one passed as a bare argument.
- **git**, while `revision: true` takes the diff: nouez turns off hooks, fsmonitor, external diff and textconv. It passes `--no-lazy-fetch`, so git never fetches a missing object. A git older than 2.45 can't do that, so there nouez takes no diff of a partial clone, a repository with a promisor remote, or one whose settings it can't read. Clean filters your repository configures (Git LFS, say) still run, as on any `git diff`.

### Credentials

nouez itself never opens a credentials file. It looks at the modification time of Claude Code's `.credentials.json`, to know when to read the sign-in line again, and nothing else. It never opens Codex's `auth.json`. The CLIs it runs read their own: `claude auth status` reads Claude Code's sign-in, and `codex login status` reads Codex's.

nouez reads `~/.claude.json` (or `$CLAUDE_CONFIG_DIR/.claude.json`) to see which folders are trusted, in `OpenClaudeSession`, `ListProjects` and the dispatcher's `setup`, `install` and `doctor` (`setup` also looks there for nouez's `consultants` registration). That file holds Claude Code's settings and some account details. To record trust (`OpenClaudeSession` with `trust: true`, or a trust mark `RestoreClaudeConfig` brings back), nouez rewrites it and keeps dated copies (see the retention table); `server.py restore`, run by you at the computer, rewrites it too, to add back one MCP server, with the same moment's race as a trust write (described under Trust). `RestoreClaudeConfig` shows each MCP server by its program or site only, never its arguments, the rest of its address or any value, so a credential in them doesn't reach the phone chat. Set `NOUEZ_NO_TRUST_WRITE=1` in nouez's environment (or `server.py settings set no_trust_write on`) and it never records trust there; only that command still writes the file. `trust: true` is then refused for a folder that isn't trusted yet, before anything, even a folder `create: true` would make, is changed. A folder you haven't trusted asks on the computer, as Claude Code does.

`OpenClaudeSession` with `resume` and `ListClaudeSessions` with `cwd` read saved transcripts to check which folder a conversation ran in. The list also reads custom titles and git branches. It masks them like a folder report and returns no message text. `ListProjects` lists folders and reads no transcripts. Separately, the status screen scans Claude Code transcripts across projects, including subagents, to count output tokens by week and model.

### Permissions

- A consultant nouez starts on Codex is read-only on every turn (sandbox `read-only`, approvals `never`). It can read what that sandbox allows, typically more than its folder, but can't change files.
- An Antigravity consultant runs under deny rules for file writes and edits, commands, MCP tools and URL actions. agy has no rule for its `schedule` tool; see [Limitations](docs/limitations.md).
- A Codex session you opened yourself keeps its own permissions. nouez refuses to message it unless Claude passes `allow_user_session: true`. Claude is told to do that only when you ask, but nouez can't check that you did. Any Claude Code session with nouez enabled can pass it, and then its message runs with that session's permissions. Set `NOUEZ_ASK_USER_SESSION=1` to approve each such message yourself, in Claude Code's own prompt, which shows the session's full id, the start of the message, how many characters it leaves out, and any model or effort sent with it; with `revision`, the prompt names the commit and the diff it will send (its SHA-256), worked out before you're asked, so your yes covers that diff and no other; when nouez can't save a diff to name, and the tree isn't clean, the message isn't sent. Your yes approves that one call: on MCP 2026-07-28, where the client sends the call again with your answer, nouez takes the answer only for the same tool with the same arguments, every one of them, so a message changed past the part shown is asked about again. Or set `NOUEZ_NO_USER_SESSIONS=1` to have nouez never message a session you opened.
- `OpenClaudeSession` starts Claude Code with your normal settings in the folder you name, and with `create: true` makes that folder. Its first prompt becomes an argument of the `claude` process, which other programs running as you can read. On Linux without `hidepid`, other users can read it too.
- `CloseClaudeSession` can end any interactive Claude Code session of the profile nouez runs under (those registered in its `sessions` folder), except the one that called it and the sessions above it; on macOS and Linux it signals nothing when it can't confirm the process is still that session.
- The phone dispatcher's sessions run with your normal settings and the dispatcher folder's. `server.py dispatcher setup` adds twelve allow rules to that folder's `.claude/settings.json`, for nouez's session tools and the phone setup's (`OpenClaudeSession`, `ListClaudeSessions`, `ListProjects`, `CloseClaudeSession`, `ListConsultants`, `ConsultantBudget`, `OpenStatusScreen`, `ArrangeWindows`, `NouezSettings`, `PhoneSetup`, `RestoreClaudeConfig`, `NouezStatus`), so from the phone those run without asking. `NouezSettings` can add a projects folder from the phone, which widens where trust can be recorded; the four switches that protect you (`no_trust_write`, `ask_trust`, `no_user_sessions`, `ask_user_session`) change only at the computer, with `server.py settings set`, or, with nouez installed as a plugin, after a yes in Claude Code's own prompt (next item). Rules already in that file, and in your user settings, still apply there: `setup` never removes one. It copies the file first (`settings.json.nouez-<date>-<time>.bak` beside it), changes nothing else in it, and leaves alone a file that isn't valid JSON, is a link or sits in a `.claude` that is a link, or changed while `setup` ran. That last check is made just before the file is replaced: a save by another program in the instant between that check and the replacement would be lost, and the dated copy holds what `setup` read. On Windows, where the folders are checked by path, they are checked again before a temporary file of `setup`'s is removed. It writes `CLAUDE.md` only where there is none. When an update adds a session tool, the supervisor adds that tool's rule the same way before it starts `claude`, only while the file still has every rule an earlier nouez gave it and once per rule (noted in `dispatcher-rules.json`), so a rule you removed isn't put back. Through `OpenClaudeSession` a dispatcher session can record trust in a folder, as any session with nouez can.
- Installed as a Claude Code plugin, nouez runs through `launch.py`, which copies the plugin's `server.py` into the plugin's data folder only when its version is higher and runs that copy; an open session moves to a newer copy only when its server says nothing is under way ([the plugin](docs/rules.md#rule-plugin-launcher)). The plugin adds a `PreToolUse` hook on `NouezSettings` (`server.py guard`): for a call that turns a protection on or off it asks Claude Code to show its own permission prompt, in the `default`, `acceptEdits` and `auto` modes, and refuses in any other. `NouezSettings` changes the protection only when the hook recorded that prompt for this change in this session, within 10 minutes, and uses the record once ([protections behind the prompt](docs/rules.md#rule-protections-behind-the-prompt)). The record ties the change to the Claude Code process running the session; a program of yours that can write the plugin's data folder could forge one, as it could run `server.py settings set` itself. The plugin's `UserPromptSubmit` hook is the same prompt hook a clone's setup adds. `/nouez:setup` adds the waiter's allow rules, and on your yes nouez's status line, to Claude Code's user `settings.json`, after a dated copy beside it; `/nouez:uninstall` takes out only those.
- `dispatcher install` adds a sign-in start that runs with your normal rights, not elevated: a Task Scheduler task `nouez dispatcher` (at your sign-in, interactive, least privilege) on Windows, a launch agent on macOS, in the home folder the system's user list names, a desktop autostart entry on Linux, whose path nouez records with the dispatcher's files so `uninstall` finds it from any shell. It runs the Python that ran `install`, with `-I`. The supervisor starts `claude` without the variables that mark a child session, and ends it, with the sessions it started from the app, when the supervisor ends: job objects on Windows, one holding the supervisor and one holding each run's `claude` from its start; its process group elsewhere, signalled until it is empty before `claude` is collected, and never once something else has collected `claude`, since its id may then be another process's. On Windows a supervisor that can't put itself in its job exits without starting `claude`. What nouez starts leaves its caller's job (`CREATE_BREAKAWAY_FROM_JOB`) only under the supervisor, so the windows it opens there and the Codex daemon outlive a run, and for Antigravity's turns, as before. A supervisor killed on macOS or Linux rather than stopped can leave its `claude` running; doctor notes it. `install` replaces, and `uninstall` removes, only a sign-in start that is nouez's: its description or label, exactly the command `install` writes (a Python by its full path, `-I`, nouez's `server.py`, told by how the file begins, `dispatcher run --folder <folder>`, the `--projects` folders or `--no-projects` it was given, an optional `--config-dir <dir>`, `--sign-in`), on Windows your account as its user, and on macOS no `Program` key. Both ask the running supervisor to stop through a request file, which counts only as a plain file, never ending a process by its id; a supervisor started at sign-in waits while they work, then starts `claude` only while nouez's start is there for its own folder and profile, and exits otherwise, or when it still can't tell after a minute. The dispatcher's files are always in `%LOCALAPPDATA%\nouez` as Windows reports it, or `~/.cache/nouez` in the home folder the system's user list names, never moved by an environment variable. On macOS `install` unloads a loaded launch agent only when launchd names nouez's plist as its source, and `uninstall` deletes the plist only once launchd no longer has it loaded. On Windows both run `schtasks` and `taskkill` from the system folder, never from the current one, and read the task with `schtasks` through `cmd /d` after `chcp 65001`, all from there too, so a path that isn't ASCII comes back as it is.
- When a server starts, it closes, once and in the background, the Codex panes nouez 0.22.0 and earlier opened. It ends only a pane whose command line is the `codex resume <id>` an earlier nouez ran, with the token it gave that pane (made with the local `pane-key`); a `codex resume` you started yourself carries none and stays open. On Windows it ends the `cmd` window running it only while nothing else runs in that window: every process in it must be that `codex` (directly or through npm's `node`) or its console, checked through handles that keep their ids from being reused, or nothing is ended. On Linux it ends the `codex` process, read from its own argument list and signalled through a pidfd opened before that read, so the signal can reach no other process. On macOS, which has no such handle, it ends nothing.
- The status screen shows text from consultants (their messages, thinking summaries, commands and replies) with control and formatting characters taken out, so a reply can't move the cursor, change colours, reorder text or send your terminal a command.
- `ArrangeWindows`, and the arranger it and the window helpers start (`server.py arrange`, Windows only), move and size only the Windows Terminal windows that show the sessions `OpenClaudeSession` opened (the status screen's window is never moved or sized: when the status screen is opened again, it is only restored if minimized and Windows is asked to bring it forward), each found through its helper's own console and checked, just before it is moved, to be Windows Terminal's and still to hold that console. Each Windows sign-in keeps its own record of them. To notice moves, it asks Windows for window events from the Windows Terminal processes holding those windows (`SetWinEventHook`, out of process): where a window is, when it is minimized or closed. It reads no window's content, keeps nothing but where nouez's own windows are, and sends nothing anywhere.

### Trust

Trusting a folder lets its Claude Code settings, hooks and MCP servers run. Apart from quiet projects in the phone dispatcher (below), nouez records trust only when Claude passes `trust: true`, and only after the same nouez server has given Claude that folder's report (conversations that share one server share that), with the folder and its files unchanged since. The other exception is a new, empty folder that the same call made with `create: true`, which has no settings to report. With `NOUEZ_ASK_TRUST=1`, nouez asks before making such a folder, so a decline leaves nothing behind. In the phone dispatcher, nouez records trust only for a folder inside one of its projects folders, kept in nouez's settings file (picked from the phone, or with `dispatcher setup --projects DIR` at the computer, up to 20; by default the one that holds the dispatcher's folder; `--no-projects` none, and then none can be added from the phone), and for a git worktree only when its main checkout is inside one too. Inside a projects folder you picked (not the default), a project whose settings files are absent or only deny, ask or set quiet options such as a theme, with nothing linked or unreadable, is trusted without the report and your yes, and the result says so; neither happens with `NOUEZ_ASK_TRUST=1` or `NOUEZ_NO_TRUST_WRITE=1` ([trust without a question](docs/rules.md#rule-trust-without-a-question)). Your home folder can be a projects folder only when picked from the phone after nouez's warning, and even then trust is never recorded for the home folder itself, nor for a folder that is, is inside or holds Claude Code's settings folder, `~/.nouez`, nouez's cache or the temporary folder. The folder must be spelled under the projects folder exactly as that is set, case included, with no link below it, and be inside it with links resolved too; on Windows, when no link is on its path, it may instead be spelled as it is on disk, so a worktree whose main checkout git keeps in another case still counts. It is checked before a folder is made, again right before `create: true` makes it, right before the write and right after it, when a failed check takes the trust back. A dispatcher with no projects folders records no trust, nor inside a projects folder that is a drive's root or is or holds your home folder, Claude Code's settings folder, nouez's cache or `~/.nouez`, also where a link takes them, or the temporary folder nouez's cache can fall back to; `dispatcher setup` refuses such a folder and `install` lists it as a problem. nouez writes trust to the one entry Claude Code's state file has for the folder, and records none when the file spells that folder more than one way and none is trusted; an entry for another folder that reads the same isn't trust. It takes back only the entry it wrote, and not when the file it compared just before writing already had trust there; a Claude Code session that saves the file in the moment between that comparison and the read-back after it can't be told apart, so its trust may be overwritten or taken for nouez's. Claude Code keeps trust for a path, so someone who can change folders inside a projects folder can later put a link where a trusted folder was, at any time and whoever recorded the trust: keep the projects folders writable only by you. This holds for the dispatcher `dispatcher install` or `dispatcher run` starts, not for the one-time `claude remote-control` run that setup asks for, which is plain Claude Code and is meant to be stopped as soon as it connects.

That proves Claude received the report; it can't prove you read it or agreed. If you want that proof, set `NOUEZ_ASK_TRUST=1`: before each recording nouez asks you in Claude Code's own prompt (MCP elicitation), which the model can't answer for you, naming the report's id, and records nothing if you decline, don't answer, or the folder's settings change while the prompt is open. Each answer approves one recording. A client that can't show such a prompt is refused. Or set `NOUEZ_NO_TRUST_WRITE=1` and answer Claude Code's own trust prompt on the computer.

nouez checks the project's settings files and their folders for links, and reports a linked one as unread, never as safe. So is a file that changes into another while nouez reads it. This is detection, not prevention: a link swapped in at that moment may let nouez read the file it points to, but what it read is then thrown away, never shown. A folder already trusted on its own needs no record, so `trust: true` there changes nothing.

### Files nouez keeps

All in your cache folder (`%LOCALAPPDATA%\nouez` on Windows, `$XDG_CACHE_HOME/nouez` or `~/.cache/nouez` elsewhere), except the backups. nouez trusts that folder itself:

- On macOS and Linux it makes the folder and the backups' folder readable by you only (0700). If the folder isn't yours or is a link, nouez uses `nouez-<uid>` in the temp folder instead.
- On Windows the folder inherits the permissions of `%LOCALAPPDATA%`, which only you can change.

Below that folder, nouez refuses to write, delete or lock any file through a link or a junction. [Files nouez keeps](docs/how-it-works.md#files-nouez-keeps) lists every file, small caches included. These are the ones that hold what you or your consultants wrote:

| What | Holds | Kept |
|---|---|---|
| `usage-log.jsonl` | One line per consultation event: project, consultant, model, effort, `kind`, `reason` (Claude's one sentence on its choice), the `base` of a branch review, tokens, each subscription's usage at a send (share used, reset and reading time). Never message or reply text. Off with `NOUEZ_NO_USAGE_LOG=1`. | Renamed each month (or past 20 MB). A renamed log goes a year after it was last written, and the oldest go first while they add up to over 100 MB. |
| `patches/` | A saved `revision: true` patch shows uncommitted changes, or with `base` the net changes since the merge base, including committed work even on a clean tree. **Tracked files and deleted lines can contain secrets.** For Antigravity, the patch text goes to Google in the message unless `attach_diff: false`. Untracked files whose path looks like a secret, binary files and untracked files over 256 KB are left out. | 14 days |
| `replies/` | Replies over 60,000 characters, or over 20,000 when the waiter (`server.py wait`) prints them | 14 days |
| `review-rounds/` | For each consultant's latest review chain, bug hunt or plan critique: the kind, the round count, its turn ids, the commit, the repository folder, the SHA-256 of the diff sent with it, and the first round's message (the brief, up to 200,000 characters), kept for a blind second opinion | 14 days after the last round |
| `agy/<id>/turns/` | Each Antigravity turn's message (with an attached diff), output and errors | Until 90 days after you stop the consultant |
| `agy/<id>/consultant.json` | The consultant's folder, name, model, standing instructions and agy conversation id | Until you delete it |
| `agy/quota-hits.json` | For each Antigravity turn that failed on its quota: its turn id, model, when it ended and the reset its error named; when a turn last succeeded on each model; and the quota group each of those models was last seen in. Never message or reply text. `quota-hits.lock` is held while it is written | Each failure until the reset it names, each success 8 days, removed at the next write; the file is replaced on each write |
| `dispatcher-claude.log`, `dispatcher.log` | What the dispatcher's `claude remote-control` printed (connection messages, the session link it shows), and the supervisor's own starts and exits | Each moved to `.1` past 1 MB, replacing the one before |
| `claude-json-backups/` (`$XDG_STATE_HOME/nouez` or `~/.local/state/nouez` on macOS and Linux) | Copies of `~/.claude.json`, which `RestoreClaudeConfig` compares with the file now (MCP servers' secrets masked, environment and header values never shown) | The newest 20 |
| `auto-close.json`, `auto-close.json.lock` | When idle consultants were last closed, and each one closed (provider, id, name, when, minutes idle), so `NouezStatus` and `doctor` can say how to bring one back; the `.lock` is held while consultants are closed | Closes older than 7 days dropped at the next sweep |
| `prompts.md` | Your own wording for nouez's prompts, if you write one (`server.py prompts`); nouez only reads it | Until you delete it |
| `settings.json` | nouez's switches when set here rather than by environment variable, the dispatcher's projects folders and where each came from, whether the phone setup is done, and what `setup --auto-update` changed, so uninstalling puts it back. `settings.lock` is held while it is written; `server.py settings reset` moves it aside as `settings.json.<date>-<time>.old` | Kept; the `.old` copies until you delete them |
| `approvals.json` (in the plugin's data folder, `~/.claude/plugins/data/nouez-<marketplace>`, only with the plugin) | For each protection change Claude Code's prompt was asked for: the change, the Claude Code process's id and start time, and when. `approvals.lock` is held while it is written | Each record until it is used or 10 minutes pass, removed at the next write |

When each goes:

- Nouez checks for expired saved diffs at server startup and when it saves a diff. It checks replies and review chains at startup and when it saves a long reply. See [when saved work is removed](docs/rules.md#rule-saved-diff-cleanup). Renamed usage logs are checked at startup and during log rotation.
- Old Antigravity turns go when a server starts.
- Extra backups go when a new one is saved.

`OpenClaudeSession` also passes a first prompt through a private temporary file, which the new window deletes once read.

Outside the cache folder, `dispatcher setup` leaves the dispatcher folder's `CLAUDE.md`, its `.claude/settings.json`, a dated copy of that file from before nouez changed it, and a dated copy of a `CLAUDE.md` an earlier nouez wrote that it replaced, until you delete them. With your yes (at the terminal, or `--statusline`), it also adds nouez's status line to Claude Code's own `settings.json`, only when that has none, and leaves a dated copy of it from before.

You can delete any of these sooner; nouez works without them. Deleting a consultant's turns while you still use it loses the conversation id nouez resumes it with, so stop it first. Codex, Antigravity and Claude Code keep their own histories in their own folders, under their own rules; nouez doesn't change those.
